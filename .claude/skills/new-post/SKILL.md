# new-post — 블로그 글 생성 스킬

이 블로그 저자의 기존 포스트 60+편을 분석해 추출한 규칙·톤·구조를 따른다.
"새 글 써줘" / "포스트 만들어줘" 같은 요청이 들어오면 이 스킬을 발동한다.

## 0. 작업 순서 (요약)

1. **주제 파악** — 사용자에게 (a) 주제, (b) 형식(아래 4가지 중), (c) 카테고리, (d) 게재 날짜를 확인. 명확하면 묻지 않고 진행.
2. **카테고리·파일명 결정** — 카테고리 폴더 확정 → kebab-case 슬러그 생성.
3. **frontmatter 작성** — 아래 규칙 그대로.
4. **본문 작성** — 아래 4가지 패턴 중 적합한 것을 골라 저자의 톤으로 작성.
5. **리소스 경로 확인** — 이미지가 있으면 `public/resource/YYYY/YYYYMMDD/` 폴더에 둠.
6. **검증** — 체크리스트(§7) 확인.

## 1. 카테고리 (폴더 = 카테고리, 모두 소문자 단일 토큰)

`src/content/posts/` 아래 다음 폴더 중 하나에만 넣는다. 새 폴더는 만들지 않는다.

| 폴더 | 어떤 글 |
| --- | --- |
| `aerospace` | 항공·우주·드론 |
| `aws` | AWS 서비스 사용기·트러블슈팅 |
| `database` | RDB/NoSQL, JPA/ORM, 쿼리·성능 |
| `etc` | 어디에도 안 맞는 일반·메타·방법론 (예: 스크럼 가이드) |
| `linux` | 리눅스 명령·셸·서버 설정 |
| `network` | 네트워크 프로토콜·구성 |
| `programming` | 언어별(Java, JS, C#, Python …) 구현·디버깅 |
| `security` | 보안·인증·취약점 |
| `softwareengineering` | 작업 일지·설계·아키텍처·SDLC |
| `system` | OS 내부·시스템 프로그래밍 |
| `tools` | 도구 사용법 (git, docker 등 단순 사용 위주) |
| `troubleshooting` | "오류 메시지 → 원인 → 해결" 사례 |
| `utility` | 유틸리티성 도구 설정 (vim, vundle 등) |
| `web` | HTTP·REST·웹 표준·프론트엔드 |

판단이 애매하면 사용자에게 `AskUserQuestion`으로 후보 2~3개를 보여주고 고르게 한다.

## 2. 파일명 (= URL 슬러그)

- **kebab-case, 영어 소문자만**. 한글·대문자·공백 금지.
- 약어도 소문자: `aws-ec2-connection.md` (X `AWS-EC2-connection.md`).
- 시리즈는 끝에 숫자: `qt-start-1.md`, `qt-start-2.md`. **이번 글이 시리즈의 일부라고 사용자가 명시했을 때만** 붙인다.
- 파일명이 곧 permalink(`/YYYY/MM/DD/slug/`)다. 한 번 게재된 파일은 함부로 rename하지 않는다.
- 새 파일 만들기 전에 같은 카테고리에 동일 슬러그가 있는지 확인.

## 3. Frontmatter

```yaml
---
title: "한글 제목"          # 따옴표로 감싸기 (콜론·물음표 안전)
subtitle: "선택. 부제목"     # 작업 일지·심화 글에서 자주 씀. 없으면 줄 자체를 뺀다
pubDate: 2026-05-20         # 단순 날짜 또는 2026-05-20T15:00:00+09:00 (KST)
category: "softwareengineering"  # §1의 폴더명과 동일
tags: ["Python", "JSON Schema"]  # 글의 실제 내용을 반영, 다른 글에서 복붙 금지
math: false                  # 본문에 LaTeX/MathJax가 실제로 있을 때만 true
draft: false                 # 공개면 false. 작성 중이면 true
---
```

규칙:
- `pubDate`는 오늘 날짜를 기본으로 한다. 사용자가 다른 날짜를 지정하면 그대로.
- `tags`는 글의 *실제 키워드* 3~6개. 카테고리와 중복돼도 무방하지만 의미 없는 일반어("정보", "공유") 금지.
- `math: true`는 수식·블록(`$...$` / `$$...$$`)이 본문에 있을 때만. 옛 글에 무의식적으로 `math: true`가 박힌 경우가 많은데 신규 글에서는 실제 사용 여부로 판단.
- 옛 포스트와 달리 신규 글은 `subtitle`이 있으면 글의 *관점*을 좁히는 한 줄로 쓴다 (예: 제목="N+1 문제", 부제="ORM 성능 문제의 핵심과 해결법").

## 4. 글의 4가지 형식 (Pattern 선택)

저자의 글은 대체로 다음 4가지 중 하나에 들어간다. 주제를 듣고 가장 가까운 패턴을 고른다.

### Pattern A — 트러블슈팅 ("오류 → 원인 → 해결")
**언제**: 구체적 에러 메시지·증상에서 출발해서 원인을 추적하고 해결한 사례.
**카테고리 후보**: `troubleshooting`, `programming`, `linux`, `aws`, `database`.

구조:
```markdown
## 문제 / 증상
재현 환경 + 에러 메시지(코드블록) + 어디서 터졌나.

## 원인 분석
1. 의심 1 → 확인 → 아님
2. 의심 2 → 확인 → 아님
3. 의심 3 → 진짜 원인 (보통 환경설정·권한·인코딩·정밀도 등)

## 해결
실제로 적용한 명령·코드·설정. 코드블록 우선.

## 정리 / 마무리 (선택)
한 줄 정리 + 같은 함정 피하는 팁.
```

### Pattern B — 개념·이론 정리 ("X는 무엇이고 어떻게 쓰나")
**언제**: REST·N+1·스크럼 스토리 분류 같은 추상 개념을 정리.
**카테고리 후보**: `web`, `database`, `softwareengineering`, `etc`, `network`.

구조:
```markdown
(1~3줄 도입 — 왜 이 주제를 다루나)

---

## 1. X란?
한 문장 정의 + 핵심 예 1개.

## 2. 왜 생기나 / 왜 필요한가
배경·원인.

## 3. 어떻게 동작하나
코드·다이어그램·표.

## 4. 함정 / 자주 묻는 것 (선택)

## 5. 정리
- 핵심 bullet 3~5개
> 마지막 한 줄을 블록인용으로 강조
```

번호 매겨진 `##` 헤더, 굵게 표시한 핵심 단어, 간헐적 `>` 블록인용이 이 패턴의 시그니처.

### Pattern C — 작업 일지 (artifact-transformer 시리즈류)
**언제**: 하루치 작업을 회고. 제목은 보통 `<프로젝트명> 작업 일지 #N`.
**카테고리**: 거의 항상 `softwareengineering`.

구조:
```markdown
> (선택) 한 줄짜리 메타 인용 — 이 글은 YYYY-MM-DD에 진행한 작업이다.

## 배경 / 발단
오늘 무엇을 손대기 시작했나. 어떤 구조였길래 손댔나.

## 문제
풀어야 했던 질문 2~4개를 번호로.

## 결정 1 — <짧은 결론>
표·코드로 근거 정리, 마지막에 결정 요약.

## 결정 2 — ...
## 결정 3 — ...

## 의도치 않은 함정
삽질 1개를 짧게.

## 마무리
1~2개 핵심 + 다음에 할 일.
```

- 제목 형식: `"artifact-transformer 작업 일지 #2"` (따옴표 안에 #).
- 부제는 *오늘의 좁은 초점*: `"산출물 출력 개선"`.
- 태그에 `"Working Log"` 포함.
- 일자 시각 `+09:00` 까지 명시: `pubDate: 2026-05-20T15:00:00+09:00`.

### Pattern D — 설정·튜토리얼 (옛 글 스타일)
**언제**: 단순 절차 안내 (alias 설정, vim 설정, 패키지 설치).
**카테고리 후보**: `linux`, `utility`, `tools`, `aws`.

구조:
```markdown
(1~2줄: 무엇이고 왜 쓰나)

## 설정 방법
명령·파일 위치.

## 자주 쓰는 예
코드블록 위주, 설명은 짧게.
```

이 패턴은 짧고 코드블록 중심. 서사 끼워넣지 말 것.

## 5. 톤·문체 (저자 목소리 보존)

신규 글의 톤은 최근(2024~)의 글을 따른다. 옛 글의 `~입니다` 톤은 신규 글에 쓰지 않는다.

- **종결어미**: 평서형 `~다`. ("~한다", "~된다", "~이다", "~다." 단정형).
  - X: "~합니다", "~입니다", "~할 거예요"
  - O: "이게 가장 흔한 원인이다.", "결국 X로 정리했다."
- **1인칭은 자제하되 회고체일 때는 허용**. 작업 일지(Pattern C)에서는 "오늘 손댔다", "낮 무렵 보고가 들어왔다" 같은 표현이 자연스럽다.
- **문단은 짧게**. 한 문단은 보통 1~3문장. 빈 줄로 분리.
- **굵게(`**`)** 는 핵심 용어·임계값에 절제해서. 한 단락에 2개 넘기지 않기.
- **블록인용 `>`** 는 한 줄 통찰·핵심 메시지·인용문에 쓴다. 본문 풀어쓰기로 대체하지 않는다.
- **표**는 비교·매핑이 있을 때만. 3컬럼 이하 권장.
- **코드블록**: 언어 태그(`bash`, `python`, `javascript`, `java`, `json`, `yaml`) 반드시 명시.
- **이모지·과한 수식어 금지**. "정말 놀랍게도", "엄청난" 같은 표현 안 씀.
- **시리즈 톤**: 결과만이 아니라 *왜 그 결정을 했는지·어떤 함정을 피했는지*를 남긴다. 단순 매뉴얼화 X.

## 6. 이미지·리소스

- 경로: `/resource/YYYY/YYYYMMDD/<filename>.png` (앞에 슬래시 있어야 정적 자산으로 풀린다).
- 실제 파일은 `public/resource/YYYY/YYYYMMDD/` 아래에 둔다 (Astro `public/` 매핑).
- 신규 글에 이미지가 없다면 굳이 만들지 않는다. 텍스트·코드·표만으로 충분한 경우가 많음.
- 이미지 alt 텍스트는 한 줄 설명(`![NFS 마운트 실패 화면](...)`). `screenshot_1` 같은 더미 alt는 피한다.

## 7. 게재 전 체크리스트

작성 직후 다음을 확인한다. 어긋난 항목이 있으면 그 자리에서 고친다.

- [ ] 파일이 올바른 카테고리 폴더에 들어가 있다.
- [ ] 파일명이 kebab-case 소문자다 (약어 포함).
- [ ] 같은 카테고리에 동일 슬러그가 없다 (있으면 URL 충돌).
- [ ] `title`이 따옴표로 감싸여 있다.
- [ ] `pubDate`가 의도한 게재 날짜다 (다른 글에서 복붙된 날짜 X).
- [ ] `category` 필드 값이 폴더명과 정확히 동일하다.
- [ ] `tags`가 이 글의 실제 키워드를 반영한다 (복붙 흔적 X).
- [ ] `math`는 본문 수식 존재 여부와 일치한다.
- [ ] 종결어미가 `~다` 평서형으로 통일돼 있다.
- [ ] 코드블록에 언어 태그가 붙어 있다.
- [ ] 이미지 경로가 `/resource/YYYY/YYYYMMDD/...` 형태이고 실제 파일이 그 위치에 있다 (이미지가 있을 때만).
- [ ] 시리즈 글이면 직전 편(`#N-1`)에서 자연스럽게 이어진다.

## 8. 사용자에게 묻기 (필요할 때만)

다음 정보가 명확하지 않으면 `AskUserQuestion`으로 한 번에 묶어서 물어본다. 이미 답이 주어졌으면 묻지 않는다.

- 글의 **주제와 형식** (Pattern A/B/C/D 중 어느 쪽?)
- **카테고리**가 애매하면 후보 2~3개 제시
- **게재 날짜**가 오늘이 아니라면 명시 요청
- **시리즈인지**, 시리즈라면 직전 편 파일명

질문은 한 번에 최소화한다. 사용자가 한 줄로 주제만 던졌으면 합리적 기본값으로 진행하고, 작성 후 사용자에게 *결정한 카테고리·파일명·형식*을 짧게 알린 뒤 수정 받는다.

## 9. 작성 완료 후 보고 형식

작성을 끝내면 다음 정보를 짧게 보고한다:

```
파일: src/content/posts/<category>/<slug>.md
카테고리: <category>
형식: Pattern <A|B|C|D>
태그: [...]
```

빌드 시도(`npm run build`)는 사용자가 요청했을 때만 한다. 기본은 파일 작성으로 마무리.
