> 이 글은 2026-11-24 오후의 기록이다. 15시 59분에 한 문장으로 시작한 아이디어가 18시 5분에 main에 병합됐다. 30분은 무엇을 만들지 정하는 데 썼고, 나머지는 12개 작업을 에이전트에게 하나씩 맡기고 검토를 붙이는 데 썼다.

## 배경 — 한 문장에서 시작했다

연말 모임에서 쓸 마니또 서비스가 필요했다. 처음 던진 말은 이것뿐이었다.

> 특정 기간 동안 마니또를 지정하고, 이에 대한 이벤트들을 모니터링하고 서로 친목을 도모할 수 있는 서비스를 개발하고 싶어.

바로 코드를 쓰지 않고 질문부터 주고받았다. 대화로 정한 것은 이렇다.

- 이미 정해진 5~10명 모임이 연말이나 워크숍 기간에 이벤트성으로 쓴다.
- 배정하고 끝나지 않는다. 기간 내내 활동이 기록되고, 모두가 피드로 본다.
- 누가 누구의 마니또인지는 종료 전까지 비밀이다.
- 미션을 주면 재밌겠다. 종료 때는 한자리에 모여 기록과 결과를 같이 본다.

## 문제

1. 활동은 누가 기록하나. 마니또가 직접 쓰면 정체가 드러난다.
2. 점수를 실시간으로 보여 주고 싶다. 그런데 점수가 움직이는 시점만으로도 배정이 샌다.
3. 5~10명이 1년에 한두 번 쓰는 서비스다. 무엇으로 만들어야 운영할 것이 가장 적은가.
4. 12개 작업을 에이전트에게 맡기면 품질을 무엇으로 지키나.

## 결정 1 — 받은 사람이 기록하고, 마니또가 몰래 판정한다

기록은 받은 사람이 쓴다. "책상에 커피가 놓여 있었어요, 마니또님 맞죠?" 같은 글이 모두의 피드에 올라간다.

그 글에는 작성자의 마니또에게만 `맞아요 / 제가 아니에요` 버튼이 보인다. 다른 사람에게는 "대기 중 / 완료" 상태만 보인다. 결과는 종료 때 한꺼번에 공개한다.

이 구조에서 재미가 두 방향으로 생긴다. 받은 사람은 마니또가 한 일이라 믿었는데 아닐 수 있다. 마니또는 자기가 한 일이 기록되지 않는 것을 지켜보게 된다. 그래서 마니또가 본인만 보는 메모로 "몰래 한 일"을 남기는 기능을 붙였다. 종료 때 "끝내 눈치채지 못한 선행"으로 공개된다.

배정은 전원이 하나의 고리(A→B→C→…→A)가 되게 한다. 자기 자신에게 배정되지 않고, 둘이 서로 마니또가 되는 일도 없다. 발표 때 고리를 따라가며 공개할 수 있다.

## 결정 2 — 실시간으로 보이는 숫자는 배정과 무관한 활동으로만 움직인다

포인트를 실시간으로 공개하자는 요구에는 함정이 있었다. B가 글을 올리고 A가 "맞아요"를 누른 직후 A의 점수가 오르면, 모두가 B의 마니또를 알게 된다. 5~10명 규모에서는 점수가 변하는 시점만으로 충분히 추리된다.

그래서 숫자를 둘로 나눴다.

| 구분 | 무엇으로 오르나 | 언제 보이나 |
| --- | --- | --- |
| 개인 참여 포인트 | 기록 작성, 미션 완료 | 실시간 |
| 모임 온도 | 모임 전체의 활동량 (36.5℃에서 시작) | 실시간 |
| 보너스 | 적중, 인정받은 선행, 판정 참여, 추측 정답 | 종료 때 합산 |

설계 문서를 검토받는 과정에서 같은 종류의 구멍이 두 개 더 나왔다.

- **판정 참여 포인트:** 대화에서는 "하루 한 번 모아 반영"하기로 했다. 그런데 그날 판정이 한 건뿐이면 점수가 오른 사람이 곧 마니또다. 종료 보너스로 옮겼다.
- **최소 인원:** 3명이면 내 대상이 아닌 나머지 한 명이 곧 내 마니또다. 비밀이 성립하지 않는다. 최소 4명으로 정했다.

오류 응답도 같은 원칙을 따른다. 마니또가 아닌 사람이 판정을 시도하면 "없는 기록"과 똑같은 오류를 돌려준다. 오류 내용으로 마니또가 누구인지 가려낼 수 없어야 한다.

설계 문서에는 목표, 비목표와 함께 **반목표**를 적었다. 기술적으로 동작해도 실패인 것들이다.

> 배정이 새는 것. 개설자가 계속 챙겨야 하는 것. 누군가를 망신 주는 것.

세 번째 때문에 순위 화면에는 등수 숫자와 "꼴찌" 표현이 없고, 발표에서는 상위 3명만 보여 준다.

## 결정 3 — Next.js 단일 앱과 PostgreSQL, 스케줄러 없이

방법을 좁히는 조건은 두 가지였다. 배정과 판정 결과는 서버만 알아야 한다. 그리고 미션 배달, 시작·마감 전환처럼 시간에 맞춰 도는 일이 있다.

| 방식 | 판단 |
| --- | --- |
| Next.js 단일 앱 + PostgreSQL | 선택. 화면과 서버가 한 프로젝트라 비밀 정보를 서버에서만 다루기 쉽다. |
| React + Spring Boot + PostgreSQL | 프로젝트가 둘이고 JVM 서버를 계속 띄워야 한다. 이 규모에는 과하다. |
| React + Supabase | 가장 빨리 뜬다. 하지만 비밀 규칙을 DB 접근 규칙으로 짜야 해서 실수하면 배정이 샌다. |

시간에 맞춰 도는 일은 스케줄러 없이 처리한다. 누군가 접속했을 때 "지금까지 밀린 것"을 계산한다. 시작 일시가 지났으면 그때 배정하고, 배달 시각이 지난 미션이 있으면 그때 내려 준다. 이벤트가 없는 열한 달 동안 돌아가는 것이 아무것도 없다.

입장은 회원가입 없이 공용 초대 링크, 이름, 4자리 PIN으로 한다. 이름만 고르게 하면 남의 이름으로 들어가 배정을 볼 수 있어서 PIN은 필요하다. 이벤트 개설은 서버 환경변수로 둔 관리 비밀번호를 아는 사람만 할 수 있다.

도구는 Drizzle, Vitest, PGlite를 골랐다. PGlite는 메모리에서 도는 PostgreSQL이라 테스트에 Docker가 필요 없다.

## 결정 4 — 작업마다 구현 에이전트 하나, 검토 에이전트 하나

구현 계획은 12개 작업으로 나눴다. 도메인 로직 8개(뼈대, 개설·입장, 배정·전환, 미션, 기록·판정, 점수, 조회, 발표 데이터), 화면 3개, 배포 1개다.

실행 방식은 둘 중에서 골랐다. 한 세션에서 12개를 순서대로 구현하고 끝에 한 번 검토받는 방식, 그리고 작업마다 새 에이전트가 구현하고 다른 에이전트가 검토한 뒤 넘어가는 방식이다. 뒤쪽이 토큰을 훨씬 많이 쓴다. 그래도 뒤쪽을 골랐다. 이 서비스는 배정이 한 번 새면 이벤트가 망가진다.

진행하면서 세 가지를 조정했다.

- 파일이 겹치지 않는 작업은 앞 작업을 검토하는 동안 다음 작업 구현을 먼저 시작했다.
- 7번 작업(보는 사람에 따라 볼 수 있는 것만 내려 주는 조회)은 비밀을 지키는 경계다. 이 작업의 검토는 더 상위 모델에 맡겼다.
- 12개가 끝난 뒤 브랜치 전체를 한 번 더 검토했다.

검토가 실제로 잡아낸 것들이 이날의 수확이다.

**PIN 잠금 우회.** 5번 틀리면 잠그는 코드가 "읽고, 1을 더해, 쓰는" 구조였다. 틀린 PIN을 동시에 여러 번 보내면 횟수가 하나만 올라간다. 4자리 PIN을 지키는 유일한 장치가 뚫려 있었다. 증가를 SQL 한 문장으로 옮겼다.

```typescript
// 동시 요청에도 횟수가 누락되지 않도록 SQL에서 원자적으로 증가시킨다.
const [counted] = await db
  .update(participants)
  .set({ failedPinAttempts: sql`${participants.failedPinAttempts} + 1` })
  .where(eq(participants.id, participantId))
  .returning({ attempts: participants.failedPinAttempts });
const lock = counted.attempts >= PIN_MAX_FAILS;
```

**시작 순간의 입장.** 시작 일시에 배정이 이뤄지는 바로 그 순간 누군가 입장하면, 그 사람이 배정에서 빠진 채 이벤트가 시작될 수 있었다. 구현 에이전트가 먼저 우려로 보고했고 검토 에이전트가 중요 지적으로 올렸다. 시작 처리는 이벤트 행을 `FOR UPDATE`로 잠그고, 입장은 같은 행을 `FOR SHARE`로 잡게 했다. 둘이 겹치면 한쪽이 기다린다.

**개설자의 계정 도용.** 최종 검토에서 나왔다. 개설자는 PIN을 초기화할 수 있다. 그러면 남의 PIN을 초기화하고 그 사람으로 들어가 대상을 볼 수 있고, 흔적도 남지 않는다. 초기화하면 그 참가자의 기존 세션을 모두 무효로 만들고, 홈 화면에 "개설자가 PIN을 초기화했어요"라는 문구가 지워지지 않게 남기기로 했다. 막을 수 없는 권한은 드러나게 만든다.

**16번에 한 번 실패하는 테스트.** 세션 토큰 변조 테스트가 마지막 글자를 바꿨다. base64의 마지막 글자는 유효 비트가 4개뿐이라, 바꿔도 같은 값으로 해석될 수 있다. 서명 중간의 글자를 바꾸게 고쳤다.

**문구.** 판정 버튼 문구가 관계를 거꾸로 적고 있었다. 결과 화면의 "남긴 기록이 없어요"는 아무것도 안 한 사람을 지목하는 표현이라 반목표에 걸려서 없앴다.

최종 검토의 지적은 13건(중요 4건, 사소 9건)이었다. PIN 잠금은 이때 한 번 더 손봤다. 잠금 시간이 5분에서 시작해 틀릴 때마다 두 배가 되고 최대 24시간까지 늘어난다. 5분 고정이면 몇 주에 걸쳐 하나씩 대입할 수 있기 때문이다.

> 구현 에이전트의 "DONE"은 주장이고, 검토 에이전트의 지적은 근거다. 동시성 문제 세 건은 모두 테스트가 통과한 뒤에 검토에서 나왔다.

## 의도치 않은 함정 — 한 번도 열어 보지 않은 화면, 그리고 작은 디스크

커밋 20여 개, 테스트 139개가 통과한 상태로 PR을 만들고 main에 병합했다. 그런데 화면은 브라우저에서 한 번도 열어 보지 않았다. 개발 서버는 직접 띄우기로 정해 두었기 때문에, 에이전트는 타입 검사와 빌드로만 확인했다. 대신 단계별 데모 데이터를 만드는 스크립트를 남겼다. 진행 중 상태와 마감 상태를 각각 만들어 눌러 볼 수 있다.

동시성 수정도 같은 한계가 있다. PGlite는 실제 잠금 동작을 보여 주지 못한다. 잠금 관련 수정은 코드 검토로만 확인했고 재현해 보지는 않았다.

저녁에는 배포를 시작했다. 서버에 Docker를 설치하고 이미지를 빌드하다가 디스크가 가득 찼다. 여유가 5GB 남짓한 서버였다. 빌드 찌꺼기를 지우고 방법을 바꿨다. 이미지는 PC에서 빌드하고, 완성된 이미지만 서버로 보낸다. 같은 날 BATON의 자체 러너도 디스크가 차서 배포가 실패했다. 하루에 두 번 같은 이유로 멈춘 셈이다.

## 마무리

- 무엇을 만들지 정하는 30분이 가장 값졌다. "점수 변동 시점으로 배정이 샌다"는 대화 단계에서 나왔고, 코드를 쓴 뒤였다면 구조를 다시 짜야 했다.
- 작업별 검토는 비쌌지만 값을 했다. 잠금 우회와 시작 순간의 경합은 테스트 통과만 봐서는 지나쳤을 문제다.

다음에 할 일은 배포를 끝내는 것과, 데모 데이터로 입장부터 발표까지 직접 눌러 보는 것이다. 설계 문서가 맞는지는 그때 처음 확인된다.
