> 이 글은 2026-11-10 하루의 기록이다. 오전에 권한 강화 커밋을 올린 뒤 "데이터가 모두 비어 있다"는 증상을 쫓았고, 그 끝에서 느린 권한 검증을 찾았다. 오후에는 그 커밋이 남긴 버그와 테스트를 정리했고, 저녁에는 여러 Task를 동시에 진행하기 위한 구조를 다섯 단계로 나눠 넣었다.

## 배경 — 권한을 매번 다시 확인하도록 바꿨다

오전에 커밋 하나를 올렸다. 파일 245개, 6만 줄이 넘는 변경이다. 내용은 세 가지다.

- 인증·작업·AI 요청·Task·초기 구축마다 **동시 실행 한도(admission)** 를 둔다.
- AI 요청에 영수증(receipt)과 작업 기록(journal)을 남겨, 중간에 끊겨도 복구할 수 있게 한다.
- 업무 데이터에 접근할 때마다 원래 권한 저장소와 요청자를 다시 확인한다.

세 번째가 이날 하루를 거의 다 쓰게 만들었다.

## 문제

1. 화면에 프로젝트 데이터가 하나도 안 보인다. 데이터가 정말 사라졌나?
2. 로그인 후 프로젝트 선택 창이 너무 느리고, 고를 때 다시 불러온다.
3. 권한 강화가 남긴 버그와 깨진 테스트를 어디까지 정리할까?
4. AI 요청과 Task 여러 개를 동시에 진행하려면 무엇이 막고 있나?

## 결정 1 — 데이터는 그대로였다, 느렸을 뿐이다

먼저 파일과 DB부터 봤다. 산출물 파일은 모든 프로젝트에 그대로 있었고, 상태 DB는 오전 백업보다 오히려 행이 늘어 있었다. 멤버십과 프로젝트 ID, 상태 행의 키도 서로 맞았다. 데이터는 없어지지 않았다.

그래서 서버를 직접 호출해 시간을 쟀다. 문서 12개짜리 작은 프로젝트의 문서 목록 요청 하나가 **39초** 걸렸다.

| 요청 | 시간 |
|---|---|
| 문서 목록 (문서 12개) | 39.15초 |
| 프로젝트 목록 | 3.34초 |
| 나머지 공통 요청 | 1초 미만 |

원인은 권한 검증의 반복이었다.

- `require_authority()`는 부를 때마다 등록된 프로젝트 **전체**의 바인딩을 처음부터 다시 검증한다. 한 번에 약 0.4초이고, 대부분은 Windows 경로 정규화를 1,400번 넘게 도는 시간이다.
- 문서 목록은 문서 하나마다 이 검증을 약 8번 부른다. 문서 12개면 100번 가까이 돈다.

화면 쪽에도 절반의 책임이 있었다. 문서·상태 데이터에 로딩 상태가 없어서, 응답이 오기 전이나 실패했을 때 모두 빈 값을 그렸다. 느린 응답이 "데이터가 비었다"로 보인 이유다.

> 느린 것과 없는 것을 화면이 구분하지 못하면, 사용자는 언제나 최악을 떠올린다.

권한을 매번 처음부터 확인하는 건 의도한 보안 설계였다. 그래서 검증을 없애지 않고 **재사용 범위**를 정했다.

- 한 요청 안에서는 처음 검증한 바인딩 결과를 재사용한다. 정책·저장소·요청자·프로젝트 등록이 바뀌었는지는 매번 확인한다.
- 요청 바깥에서는 여전히 매번 검증한다.
- 한 번의 검증 안에서 저장된 바인딩을 프로젝트 수만큼 다시 읽던 것을 한 번만 읽게 했다.
- 서버 시작 때 프로젝트 목록 캐시를 백그라운드에서 미리 채운다.
- 화면은 응답 전에 "불러오는 중…"을, 실패하면 오류 문구를 보여 준다.

| 항목 | 전 | 후 |
|---|---|---|
| 프로젝트 권한 검증 1회 | 약 0.4초 | 0.12~0.2초 |
| 문서 목록 1건 | 39초 | 약 6~11초 |
| 재시작 직후 첫 목록 | 약 5초 | 사전 조회로 단축 |

프로젝트 선택 시 "다시 불러오는" 것처럼 보이던 요청은 목록 재요청이 아니라 참여 권한 재확인이었다. 이건 테스트가 필수로 요구하는 동작이라 남기고, 검증 자체를 빠르게 하는 쪽으로 해결했다.

## 결정 2 — 권한 강화의 뒷정리는 하루 안에 끝낸다

속도를 고치자 가려져 있던 문제들이 드러났다.

**검토 기록의 옛 형식.** 기존 검토 기록 87건에 작성자 신원이 없어서 진행 현황 API가 늘 503을 냈다. 이전 전 DB를 백업하고, 최근 기록에 이미 저장된 같은 신원으로 채웠다. 검토자 이름이 비어 있던 기록은 지어내지 않고 "미배정"으로 뒀다. 적용 전에 서버의 실제 검증 함수로 87건을 모두 통과시켰다.

**초기화 미리보기 버그.** `state.get_workspace`가 권한 저장소를 필수 인자로 받게 바뀌었는데, 온보딩의 `reset_preview`와 `reset`은 인자 없이 부르고 있었다. 결과는 바로 `TypeError`였다. 라우트가 현재 사용자의 프로젝트 권한을 다시 확인해 넘기도록 고쳤고, 아직 프로젝트를 만들지 않은 세션은 기존과 같은 "초기 구축으로 만든 프로젝트만 초기화할 수 있다" 오류를 받는다.

**Jira 연결 저장소.** 연결 정보가 새 저장소로 옮겨졌는데, 서버는 이 저장소를 스스로 만들지 않는다. 운영자가 한 번 전환해 줘야 한다. 기존 정보와 암호화 키를 백업하고, 최신 형식의 연결 1건만 새 저장소로 옮긴 뒤 옛 파일은 이름만 바꿔 보관했다.

**테스트.** 온보딩 테스트 실패 43개가 0개가 됐다. 원인은 권한 인자를 빠뜨린 옛 호출, 준비하지 않은 DB 스키마, 느린 PC에서 너무 짧았던 대기 시간(30초 → 180초)이었다.

## 의도치 않은 함정 — `'$GIT_DIR' too big`

저장소 테스트가 11개 실패했다. 변경 전 코드에서도 똑같이 실패해서 처음에는 원래 있던 문제로 분류했다.

다시 보니 Git 오류 메시지가 `'$GIT_DIR' too big`이었다. 테스트 임시 폴더를 너무 긴 경로 아래에 둔 탓이었다. 짧은 경로로 옮기자 11개가 2개로 줄었다.

"변경 전에도 실패한다"는 내 변경이 원인이 아니라는 증거일 뿐, 코드가 원인이라는 증거는 아니다. 실행 환경이 공통 원인일 수 있다.

## 결정 3 — 동시 작업은 실행 한도보다 초안 분리가 먼저다

저녁에는 "여러 AI 지시와 Task를 동시에 수행하려면?"이라는 질문을 검토했다. 이미 되는 것과 막고 있는 것을 나눠 봤다.

이미 되는 것은 꽤 많았다. AI 대화와 변경안은 요청한 Task에 남고, 요청은 서버에 영수증으로 남아 Task를 바꿔도 계속 돈다. 세션이 다르면 활성 Task도 따로 둘 수 있다.

막고 있는 것은 두 가지로 좁혀졌다.

| 막는 요소 | 현재 | 영향 |
|---|---|---|
| 생성·발행 작업 한도 | 서버 전체 1건 | 다른 사람의 발행까지 줄을 선다 |
| 개인 초안 | 사용자 × 프로젝트 × **문서**당 1개 | Task를 바꾸면 초안이 모두 지워진다 |

두 번째가 더 컸다. 같은 문서를 두 Task가 고치는 일이 드물더라도, Task를 바꾸는 순간 저장하지 않은 변경이 모두 폐기되니 애초에 여러 Task를 오갈 수 없었다.

추천 순서대로 나눠 넣었다.

1. **실행 한도 조정** — 생성·발행은 서버 전체 3건, 사람당 2건으로 올렸다. 같은 프로젝트는 Git에 쓰므로 계속 1건씩이다. AI 요청의 사람당 한도는 2건에서 3건이 됐다. 전체 한도만 낮춰 둔 기존 설정은 개인 한도가 자동으로 따라 내려가 그대로 유효하다.
2. **진행 중인 AI 요청 목록** — Task 큐 위에 모든 Task의 결과 미수령 AI 요청을 보여 준다. 기존 작업 기록과 읽기 전용 상태 조회만 쓰고, 요청을 다시 보내거나 적용하지 않는다.
3. **Task별 초안** — 설계 문서부터 썼다.

3번의 핵심은 새 저장소를 만들지 않는다는 점이다. 검토 편집은 이미 `review:<검토ID>:<문서>` 이름으로 따로 저장되고 있었다. 이 방식을 Task로 넓혀 `task:<Task키>:<문서>`에 저장한다. 개인 작업공간이 이미 (종류, 이름) 형태의 범용 저장소라서 서버 스키마 변경도, 데이터 이전도 필요 없다.

설계에서 정할 것 네 가지는 모두 제안대로 갔다.

- 기존 초안은 "작업 미지정"으로 보이고, 사용자가 고를 때만 현재 Task로 가져온다. 가져오기는 Task 쪽 저장을 확인한 뒤에만 원본을 비우고, Task에 같은 문서 초안이 있으면 덮어쓰지 않는다.
- Task 전환은 "폐기 후 전환"에서 "저장 확인 후 전환"으로 바꾼다. 저장을 확인하지 못하면 전환하지 않는다.
- 같은 문서를 다른 Task도 고치고 있으면 편집을 막지 않고 경고만 띄운다. 겹친 항목은 반영할 때 기존 필드 단위 충돌 해결 화면으로 정리한다.
- Task를 완료할 때 남은 초안이 있으면 "검토 요청 / 그대로 두고 완료 / 버리고 완료" 중에서 고른다. 버리기는 서버가 완료를 받아들인 뒤에만, 그 Task의 초안만 지운다.

다섯 단계를 커밋 세 개로 나눠 올렸다. 웹 테스트는 3,523개다. 다만 완료 시 선택 창이 뜨고 고른 대로 처리되는 흐름은 아직 자동 테스트가 없다.

## 마무리

- "데이터가 비었다"는 신고의 원인은 데이터가 아니라 반복 검증과 로딩 상태 부재였다. 보안 검증은 없애지 않고 한 요청 안에서만 재사용했다.
- 동시 작업을 막던 건 실행 한도보다 문서 단위 초안이었다. 이미 있던 검토 범위 이름 규칙을 Task로 넓혀 스키마 변경 없이 풀었다.

다음에 할 일은 두 가지다. 브라우저에서 Task 전환과 완료 흐름을 직접 확인하는 것, 그리고 Task별 초안이 실제로 쌓인 뒤 개인 작업공간 응답 크기를 재는 것이다. 목록이 느려지면 그때 서버에 접두어 조회를 넣는다.
