> 이 글은 2026-11-12 하루의 기록이다. 오전에는 전날 미뤄 둔 안정성 항목과 낡은 서버 테스트를 정리했고, 낮에는 AI 변경안이 왜 실패했는지 화면에 보이게 했다. 저녁에는 한 달 만에 로컬 도커 배포를 다시 올렸는데, 그동안 쌓인 차이가 한꺼번에 드러났다.

## 배경 — 미뤄 둔 것 세 가지와 한 달 된 이미지

전날 일지 끝에 다음 할 일을 세 가지 적었다. 다른 패널에도 "새로고침 뒤 대화 차단"이 있는지 확인하기, 마크다운 링크 걸러 내기, 이 작업 전부터 실패하던 서버 테스트 네 파일 정리하기다.

아침에 "시스템 안정성 개선"이라는 한 줄로 이 셋을 모두 진행했다. 그러던 중 화면에 "AI 변경안을 완료하지 못했습니다"라는 문구만 뜨는 실패를 만났고, 하루의 절반이 그쪽으로 넘어갔다.

도커 쪽은 사정이 달랐다. 로컬 도커 배포의 이미지는 10월 13일에 만든 것이었다. 그 사이 서버에는 필수 설정과 테이블이 계속 추가됐지만 도커로는 한 번도 올려 보지 않았다.

## 문제

1. 서버 테스트가 왜 깨진 채로 방치됐나? 깨진 쪽은 테스트인가, 서버인가?
2. AI 요청이 실패했을 때 사용자는 무엇을 알아야 하나? 어디까지 보여 줘도 안전한가?
3. 한 달 묵은 도커 배포를 최신으로 올리려면 무엇이 맞아야 하나?
4. 사람이 한 번 해 줘야 하는 초기화를 재배포마다 반복하지 않으려면?

## 결정 1 — 낡은 테스트는 서버를 건드리지 않고 계약에 맞춘다

먼저 웹 쪽 세 가지를 끝냈다.

- **확인 질문 패널**: 전날 질문 패널에서 고친 것과 같은 차단 버그가 있었다. 결과가 저장되는 동안 입력란에 글을 쓰면 새로고침 뒤 그 Task의 확인 질문이 막힌다. 재현 테스트를 먼저 쓰고 같은 방식으로 고쳤다. 변경안 패널은 코드를 읽어 보니 같은 위험이 없어 손대지 않았다.
- **링크**: AI 답변과 문서의 링크는 http·https, 메일, 문서 안 경로만 열린다. `javascript:`나 `data:` 링크는 일반 글자로 표시한다.
- **의존성**: 푸시할 때 뜨던 취약점 경고 3건은 빌드 도구 버전을 올려 `npm audit` 0건으로 만들었다.

서버 테스트는 처음 알던 네 파일을 고치고 나서 AI 관련 묶음 45개 파일을 돌렸더니 일곱 파일이 더 나왔다. 실패 80건, 오류 125건이었다.

이게 오늘 변경 때문인지부터 확인해야 했다. 변경 전 커밋을 별도 작업 폴더에 꺼내 같은 일곱 파일을 돌리고 실패 목록을 비교했다. 한 건만 빼고 같았고, 그 한 건은 단독으로 돌리면 통과했다. 기존 문제로 확정했다.

원인은 거의 전부 테스트가 현재 서버 계약을 따라오지 못한 것이었다.

| 유형 | 내용 |
|---|---|
| 권한 인자 누락 | 저장소·검토·삭제 호출에 `authority` / `require_authority`가 빠져 있다 |
| 소유자 키 | 계정 단위 값을 기대하는데 서버는 로그인 세션 단위로 바뀌었다 |
| 프로젝트 헤더 | AI 요청 조회·취소 호출에 프로젝트 ID 헤더가 없어 404가 난다 |
| 가짜 저장소 | 읽기 함수가 없는 가짜 문서 저장소를 쓴다 |

서버 코드는 한 곳만 바꿨다. 유스케이스 번호가 겹쳐 삭제하지 못할 때의 안내가 사용자에게 보이지 않던 것이다. 기대값을 바꾼 곳도 하나 있다. AI 처리 중 프로젝트가 재등록되면 테스트는 503을 기대했지만 서버는 403을 낸다. 같은 상황을 403으로 확인하는 통과 테스트가 이미 있어서 그쪽에 맞췄다.

정리 후 실패하던 일곱 파일과 새 테스트 두 파일을 한 번에 돌려 587건이 통과했다.

방치된 이유는 단순했다. CI 설정에 서버 테스트를 돌리는 단계가 없었다. 파일 하나가 9~15분씩 걸려서 손으로도 전체를 잘 돌리지 않는다. 서버 전체 163개 파일은 이번에도 돌리지 않았다.

> 아무도 돌리지 않는 테스트는 계약이 바뀔 때마다 조용히 낡는다.

## 결정 2 — 실패 원인은 서버가 직접 쓴 문장만 보여 준다

"AI 변경안을 완료하지 못했습니다"만 나오던 이유는 서버에 있었다. AI 오류를 잡으면 실제 원인을 버리고 이 한 줄만 돌려주고 있었다.

일부러 그렇게 만든 것이다. AI 공급자의 오류 원문에는 비밀값이 섞일 수 있다. 문제는 서버가 직접 작성한 안전한 설명까지 같이 버려졌고, 로그에도 남지 않았다는 점이다.

기준을 다시 잡았다.

- 사용자에게는 **서버가 직접 쓴 진단**만 보여 준다. 원인, 실패 단계, 대상 파일, 다음에 할 일, 오류 ID다.
- 공급자 원문은 계속 숨긴다. 대신 오류 ID와 함께 서버 로그에 전문을 남긴다.

화면은 거의 고칠 것이 없었다. 변경안 패널은 이미 이 항목들을 표시할 수 있었고, 서버가 보내지 않았을 뿐이다.

최근 실패 기록을 살펴보다가 다른 원인도 찾았다. 6건 중 4건은 AI 문제가 아니었다. 요청이 2~6분 걸리는 동안 로그인이 만료되어 서버가 결과를 거부한 것이다. 이 경우 화면에는 영문 문구가 그대로 나왔다. "로그인이 만료되어 완료하지 못했습니다. 다시 로그인한 뒤 같은 지시를 다시 보내세요"로 바꿨다. 긴 요청 중 토큰이 만료되면 결과가 버려지는 구조 자체는 그대로다.

고친 효과는 오후에 바로 확인됐다. 같은 실패가 다시 났는데 이번에는 원인이 보였다.

```text
AI 변경안을 완료하지 못했습니다.
원인: Codex CLI 응답 실패: 모델 id 를 확인하세요
실패 단계: 변경 범위 검토
```

설정에 저장된 모델을 로그인된 계정으로 더는 쓸 수 없게 된 것이었다. 오전 11시까지는 정상 응답했고 오후 4시 요청이 5초 만에 거절됐다.

다만 이 문구도 부족했다. 어떤 모델이 거절됐는지, 무엇으로 바꾸면 되는지 알려 주지 않는다. 거절된 모델 이름과 지금 쓸 수 있는 모델 목록을 원인에 함께 붙였다. 목록은 Codex가 직접 알려 준 것이 있을 때만 붙인다.

같은 흐름에서 화면 두 곳을 더 손봤다. 변경 내역 카드는 영역이 좁으면 버튼이 문서 이름 위에 겹쳐 그려졌다. 이름 영역 폭이 고정이었기 때문이다. 자리가 부족하면 버튼이 둘째 줄로 내려가게 하고, 네 가지 폭에서 겹치지 않는지 검사하는 화면 테스트를 넣었다. "자료 전환 후 확인할 내용" 목록은 아예 없앴다. 전환 시점에 이미 현재 편집 값으로 처리되고, 남겨 둬도 어떤 기능도 막지 않는 목록이었다.

## 결정 3 — Keycloak을 같은 Compose 구성에 넣는다

`docker compose up --build` 한 번이면 될 줄 알았던 배포는 세 번 막혔다.

| 막힌 곳 | 원인 |
|---|---|
| 이미지 빌드 | 읽을 수 없는 `.pytest_cache` 폴더에서 빌드 컨텍스트 수집이 멈춘다 |
| API 시작 | 새 서버가 요구하는 SSO 주소 세 개가 도커용 설정에 없다 |
| API 시작 | 도커 쪽 DB에 그 뒤 추가된 테이블이 없다 (23개 대 40개) |

두 번째는 전날 아침 네이티브 서버에서 겪은 것과 같은 설정이다. 그때 네이티브용 설정만 채웠고 도커용은 생각하지 않았다.

새 이미지가 시작에 실패하는 동안 도커 쪽 서비스가 몇 분씩 멈췄다. 교체 전에 기존 이미지를 태그로 남겨 뒀기 때문에 바로 되돌릴 수는 있었다.

SSO 설정은 값을 채우는 대신 구조를 바꿨다. 지금까지 Keycloak은 따로 띄운 컨테이너였고, API 컨테이너는 호스트를 거쳐 HTTP로 붙었다. Keycloak을 BATON의 Compose 구성에 서비스로 넣었다.

- 기존 데이터 볼륨과 인증서를 그대로 물린다. 계정과 realm 설정을 다시 만들지 않는다.
- API는 Keycloak이 준비된 뒤 시작한다.
- 새 서버가 요구하는 SSO 주소와 CA 인증서를 이 구성 파일에서 넣는다.

DB는 네이티브 데이터로 덮어쓰기로 했다. 한 달 사이 도커 쪽에서만 한 작업은 사라진다. 따로 한 작업이 없어서 그대로 진행했다.

데이터를 옮기는 스크립트도 낡아 있었다. 프로젝트별 DB를 하나로 합치는 예전 구조 기준이라 중간에 `UNIQUE constraint failed`로 멈췄다. 지금은 네이티브가 DB 하나에 다 담고 있으므로, 그 DB를 그대로 복사하고 경로만 컨테이너 기준으로 바꾸도록 다시 썼다. 스냅샷에 네이티브 경로가 남아 있으면 그 단계에서 바로 실패하게 했다.

빌드 실패의 실제 원인은 `.dockerignore`의 예외 규칙이었다.

```text
!config/system/*.env.example
```

`!` 규칙이 있으면 Docker는 제외된 폴더 안까지 열어 본다. 그래서 권한이 깨진 임시 폴더에서 멈췄다. 이 예외는 처음부터 필요가 없었다. `*.env` 패턴은 `*.env.example`과 일치하지 않는다. 예외 다섯 줄을 지우자 읽을 수 없는 폴더가 남아 있어도 빌드가 됐다.

배포가 끝난 뒤에는 정리를 길게 했다. 옛 프로젝트 경로에 남아 있던 Task 39건을 현재 경로로 옮기면서 번호가 겹쳐 뒤 번호로 다시 매겼다. 그 과정에서 만든 DB 백업, 이전 이미지 태그, 배포 기록 폴더, 일회성 스크립트는 확인 후 모두 지웠다. 이제 오늘 이전 상태로는 되돌릴 수 없다.

## 결정 4 — 초기화는 여러 번 실행해도 안전한 명령으로 만든다

배포 후 Jira 연결을 누르자 "Jira 승인 상태 저장소의 초기화 또는 복구가 필요합니다"가 떴다.

OAuth 저장소는 데이터를 옮길 때 일부러 복사하지 않았다. Jira 토큰은 쓸 때마다 바뀌어서 네이티브와 도커가 같은 토큰을 쓰면 한쪽이 끊긴다. 그리고 새 서버는 이 저장소를 스스로 만들지 않는다. 관리자 인증을 가진 운영자가 한 번 명시적으로 초기화해야 한다.

처음에는 그 절차를 손으로 따라갔다. 관리자 계정으로 로그인 화면 절차를 거쳐 토큰을 받고, 서버의 검증기를 통과시킨 뒤 공식 초기화 함수를 불렀다. 인증을 꾸며서 건너뛰는 길은 택하지 않았다. 그 보호 장치를 둔 이유가 없어지기 때문이다.

Google 연동 저장소까지 같은 일을 하려다 보니 문제가 둘 더 보였다. 하나는 Google 토큰이 이미지 안 경로에 저장된다는 것이다. 컨테이너를 다시 만들면 사라진다. 다른 하나는 재배포할 때마다 이 손작업을 반복해야 한다는 것이다.

그래서 초기화를 명령으로 만들었다.

```bash
python -m server.oauth_setup
```

- 없는 저장소만 만들고, 이미 있는 저장소는 건드리지 않는다. 매 배포마다 실행해도 된다.
- 관리자 토큰은 서버가 직접 검증한다. 관리자가 아닌 계정은 거부한다.
- Google 토큰 위치는 설정으로 바꿀 수 있게 하고, 도커에서는 유지되는 폴더를 가리키게 했다.

검증은 실제 도커에서 했다. 초기화를 두 번 연속 실행해도 Jira 저장소는 그대로였다. Google은 임시 클라이언트 파일로 확인했다. 첫 실행에서 만들어지고, 컨테이너를 교체한 뒤 다시 실행하면 기존 것을 그대로 썼다.

Google 연동 자체는 아직 켜지 못했다. OAuth 클라이언트 파일이 없다.

## 의도치 않은 함정 — 프로젝트를 열면 목록으로 튕겨 나갔다

도커 배포가 끝나고 모든 컨테이너가 정상이라고 나왔다. 그런데 프로젝트를 선택하면 불러오다가 다시 목록 화면으로 돌아갔다.

로그를 보니 프로젝트를 열 때 호출되는 코드 저장소 조회가 503이었다. 웹은 이 응답 코드를 "프로젝트 권한을 확인할 수 없음"으로 해석해 선택을 해제하고 목록으로 돌려보낸다.

503의 원인은 경로 비교였다. 서버는 프로젝트 설정 파일의 `WORK_DIR`이 실제 작업 폴더와 같은지 검사한다. 도커는 네이티브와 같은 설정 파일을 읽는데, 거기 적힌 값은 Windows 경로다. 리눅스 컨테이너에서는 절대 경로로도 인식되지 않는다.

도커에서는 작업 폴더 위치를 별도 파일로 덮어쓴다. 그런데 이 검사는 덮어쓴 값이 아니라 설정 파일의 원래 값을 보고 있었다. 10월 이미지에는 이 검사가 없어서 드러나지 않았을 뿐이다.

고치는 길은 둘이었다. 도커용 설정 파일을 따로 두거나, 서버가 덮어쓴 경로를 비교하게 하거나. 설정 파일을 두 벌로 관리하고 싶지 않아서 서버를 고쳤다. 덮어쓴 경로가 실제 작업 폴더와 다르면 여전히 거부한다.

컨테이너 상태와 `/health`가 모두 정상이어도, 로그인한 뒤의 첫 화면은 따로 눌러 봐야 알 수 있었다. 헬스 체크는 "서버가 떴다"까지만 말해 준다.

## 마무리

- 실패 문구는 "숨길 것"과 "버릴 것"을 구분해야 한다. 공급자 원문은 숨기되, 서버가 직접 쓴 진단은 사용자에게 가야 한다. 그 차이 덕분에 오후의 모델 거절은 원인을 바로 찾았다.
- 한 달 동안 올리지 않은 배포는 그 한 달의 변경을 한 번에 치른다. 필수 설정, 스키마, 경로 검사, 데이터 스크립트가 모두 같은 날 터졌다.

확인하지 못한 것도 적어 둔다. 실패 원인 화면, 좁은 변경 내역 카드, 도커에서의 로그인과 프로젝트 열기는 브라우저에서 직접 보지 않았다. 프로젝트 경로 검사는 새 컨테이너 안에서 14개 프로젝트를 대상으로 돌려 본 것이 전부다. 권한이 깨진 임시 폴더 39개는 관리자 권한으로 정리 스크립트를 실행해야 지워진다.

다음에 할 일은 네 가지다. CI에 서버 테스트 단계를 넣는 것, 긴 AI 요청 중 로그인이 만료되면 결과가 버려지는 구조를 고치는 것, 예상치 못한 예외로 AI 작업이 실패할 때 서버 로그에 아무것도 남지 않는 문제를 막는 것, 그리고 코드 저장소 조회 하나가 실패했다고 프로젝트 전체에서 내보내는 반응이 맞는지 다시 보는 것이다.
