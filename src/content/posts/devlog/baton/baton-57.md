> 이 글은 2026-11-25 하루의 기록이다. 오전에는 Keycloak 로그인 화면에 BATON 테마를 입혔고, 접속할 수 없는 개발 서버에는 워크플로로 적용했다. 오후에는 "배포하면 진행 중이던 작업이 초기화된다"는 증상을 추적해 웹과 서버 세 곳을 고쳤다. 저녁에는 27분 동안 멈춰 있던 AI 진행 화면의 원인을 찾았다.

## 배경 — 자동 배포가 드러낸 것

#56에서 develop 푸시가 곧 개발 서버 배포가 됐다. 이날도 푸시할 때마다 서버가 다시 떴다. 배포가 잦아지자 그동안 가려져 있던 증상이 보이기 시작했다. 배포가 끝나면 열어 둔 프로젝트가 닫혀 있고, 시작해 둔 작업을 다시 골라 시작해야 했다.

그 전에 오전에는 다른 일을 했다. BATON 웹의 로그인 진입 화면과 Keycloak의 로그인 화면이 서로 다른 제품처럼 보였다.

## 문제

1. Keycloak 로그인 화면을 BATON 모양으로 바꾸되, Keycloak 업그레이드에 깨지지 않게 하려면 어디까지 덮어써야 하나.
2. 개발 서버의 Keycloak에는 접속 권한이 없다. 테마를 어떻게 올리나.
3. 배포할 때 무엇이 초기화되나. 정말 데이터가 지워지나.
4. AI 지시 화면이 27분 동안 "서버 상태를 받지 못했다"는 문구만 보여 줬다. 서버가 멈춘 것인가.

## 결정 1 — 로그인 테마는 템플릿을 건드리지 않는다

테마는 `deploy/keycloak/themes/baton/login`에 만들었다. 기본 테마 `keycloak.v2`(PatternFly 5)를 부모로 두고, 덮어쓴 것은 네 가지뿐이다. CSS, 하단 문구용 `footer.ftl`, 한국어·영어 메시지 파일이다.

```properties
# theme.properties
parent=keycloak.v2
```

화면 템플릿(`.ftl`)을 복사해 고치면 모양은 자유롭지만, Keycloak이 템플릿을 바꿀 때마다 따라가야 한다. 그래서 스타일만 얹었다. 다크 모드는 `html.pf-v5-theme-dark` 선택자로, 브랜드 문구는 `loginTitleHtml` 메시지로 넣었다.

확인은 쓰고 있는 Keycloak이 아니라 일회용 컨테이너에서 했다. 다른 포트에 볼륨 없이 띄우고, 헤드리스 브라우저로 로그인·오류·비밀번호 재설정 화면을 찍어 본 뒤 지웠다. OTP와 소셜 로그인 화면은 띄워 보지 못했다.

적용할 때 알아 둘 것이 두 가지 있었다.

- 운영 모드(`start`)는 테마를 캐시한다. 테마 파일을 바꾸면 재시작해야 한다. `start-dev`는 새로고침으로 반영된다.
- realm의 Localization이 꺼져 있으면 메시지 파일에 한국어가 있어도 화면은 영어로 나온다.

## 결정 2 — 접속할 수 없는 서버는 워크플로로 고친다

로컬은 컨테이너를 다시 만들고 realm의 Login theme을 `baton`으로 지정하면 끝났다. 개발 서버가 문제였다. 서버의 Keycloak은 CD가 건드리지 않는 별도 Compose 구성이고, 그 서버에 들어갈 권한이 없다.

#56에서 러너 디스크를 비울 때와 같은 방법을 썼다. 자체 러너가 그 서버에서 돌고 있으니, 워크플로를 하나 추가해 러너가 대신 하게 했다. `.github/workflows/keycloak-theme.yml`이 하는 일은 이렇다.

1. 테마 파일을 Keycloak에 넣는다.
2. 내용이 바뀌었을 때만 Keycloak을 재시작하고 healthy를 기다린다.
3. realm의 Login theme을 `baton`으로 맞춘다.
4. realm의 Localization을 켜고 기본 언어를 한국어로 맞춘다. 이미 제공하던 언어는 그대로 둔다.

첫 실행은 실패했다. 서버의 Keycloak 컨테이너가 테마 폴더 마운트 없이 떠 있어서, 넣을 곳을 찾는 단계에서 멈췄다. 마운트가 없으면 컨테이너 안으로 직접 복사하도록 고친 뒤 통과했다. 관리자 로그인은 컨테이너의 bootstrap 관리자 계정으로 통과해서 GitHub 시크릿은 등록하지 않았다.

푸시 전에는 워크플로의 각 단계 스크립트를 YAML에서 꺼내 일회용 Keycloak에 돌려 봤다. 언어 설정 단계는 두 번 돌려서, 두 번째에는 아무것도 바꾸지 않는 것을 확인했다.

| 실행 | 결과 |
| --- | --- |
| 1차 | 실패. 서버 컨테이너에 테마 마운트가 없음 |
| 2차 | 설치, 재시작, realm 설정까지 성공 |
| 3차 (언어 추가) | 언어 "없음 → ko, en (기본 ko)". 테마는 그대로라 재시작 없음 |

남은 약점도 적어 둔다. 테마가 컨테이너 안에 들어가 있어서, 컨테이너를 다시 만들면 사라지고 로그인 화면은 기본 테마로 돌아간다. 워크플로를 다시 돌리면 복구된다. 서버 컨테이너를 마운트가 있는 구성으로 다시 만들어야 근본적으로 없어진다.

> 접속 권한이 없는 서버라도 그 서버에서 러너가 돈다면, 변경을 코드로 적어 푸시하는 길이 남아 있다. 손으로 한 설정과 달리 기록도 남는다.

## 결정 3 — 연결 실패는 "권한 없음"이 아니다

오후의 질문은 이것이었다. "배포할 때 진행 중인 데이터가 모두 초기화되는 것 같다."

먼저 지워지는 것이 있는지 봤다. 배포 스크립트는 이미지를 받아 컨테이너만 바꾼다. 프로젝트 산출물과 상태 DB는 호스트 폴더에 묶여 있어 그대로 남는다. 서버가 시작하면서 테이블을 비우는 코드도 없었다. 데이터는 지워지지 않았다.

원인은 웹에 있었다.

- 프로젝트를 연 상태에서 웹은 30초마다, 그리고 창에 포커스가 올 때마다 프로젝트 목록을 다시 받는다.
- 배포로 API가 잠깐 내려간 사이 이 요청이 한 번 실패하면, 웹은 이를 "권한을 확인할 수 없음"으로 처리했다.
- 그 처리에서 프로젝트 선택이 풀리고, 시작한 작업과 열어 둔 문서가 닫혔다. 브라우저에 보관하던 미저장 편집 복구 기록도 모든 프로젝트에 대해 삭제됐다.

권한이 사라졌을 때 화면을 내려놓는 것은 맞는 동작이다. 문제는 네트워크 오류와 502를 권한 거부와 같은 것으로 본 점이다.

"작업을 다시 시작해야 한다"는 증상에는 원인이 하나 더 있었다. 작업 시작 상태는 서버에 계정이 아니라 **로그인 세션** 단위로 저장된다. 세션이 바뀌면 이전 세션의 작업은 서버에 남아 있어도 새 세션에는 보이지 않는다. 로컬 상태 DB에 흔적이 있었다. 같은 계정의 같은 작업이 사흘에 걸쳐 서로 다른 세션으로 세 번 시작돼 있었다.

세 가지를 고쳤다.

| | 바꾼 곳 | 내용 |
| --- | --- | --- |
| A | 웹 | 목록 확인이 연결 실패나 502·503·504로 실패하면 선택, 작업, 미저장 편집을 그대로 두고 다음 주기에 다시 확인한다 |
| B | 서버 | 재시작 직후 Keycloak에서 서명 키를 받지 못하면 401 대신 503으로 답한다 |
| C | 서버 | 새 로그인 세션에 작업이 없으면 같은 계정의 직전 세션 작업을 이어받는다 |

B는 A와 짝이다. 웹은 401을 받으면 로그인 정보와 복구 기록을 지운다. 그런데 서버가 서명 키를 받지 못한 것은 토큰이 틀린 것이 아니라 서버가 아직 확인할 수 없는 것이다. 키 ID가 맞지 않는 토큰은 여전히 401이다. 배포 때 실제로 이 경로를 타는지는 확인하지 못했다.

C는 설계를 바꾸는 결정이었다. "세션마다 따로 작업한다"가 원래 설계였고, 그것을 검사하는 테스트도 있었다. 이어받기에는 조건을 붙였다. 새 세션에 진행 중 작업과 이력이 모두 없을 때만 가져온다. 이전 세션의 기록은 지우지 않는다. 다른 브라우저에서 아직 열려 있을 수 있어서다. 새 세션에서 작업을 내려놓으면 다시 끌어오지 않는다.

기존 테스트 4건이 이 변경과 충돌했다. "두 번째 로그인 세션은 빈 상태로 시작한다"를 검사하던 1건과, 키 조회 실패를 401로 기대하던 3건이다. 실패가 아니라 설계가 바뀐 것이라 기대값을 고쳤다. 관련 서버 테스트 723건과 웹 접근 테스트 106건이 통과했다.

> 일시 장애와 거부를 같은 오류로 처리하면, 가장 조심스러운 코드가 가장 많이 지운다.

## 결정 4 — 조용해진 연결은 웹이 먼저 포기한다

저녁에 다른 보고가 들어왔다. 개발 서버에서 AI 지시를 했는데, 27분 동안 "서버 상태를 받지 못했다"는 문구만 나왔다.

서버는 정상이었다. 헬스 체크가 바로 응답했고, 마지막 배포는 그보다 한참 전에 끝나 있었다. 서버는 AI 요청이 도는 동안 5초마다 상태 신호를 보내고, 웹은 그 신호를 20초 넘게 못 받으면 이 문구를 띄운다.

API가 죽었거나 재시작됐다면 프록시가 연결을 닫아 "연결이 끊겼다"는 오류가 떴어야 한다. 오류 없이 시간만 올라갔다. 연결이 통보 없이 죽은 것으로 보인다. 네트워크 전환이나 절전 같은 경우인데, 어느 것인지는 가려내지 못했다. 서버 로그에도 접근하지 못했다.

확실한 것은 웹 쪽 결함이다. 웹은 신호가 끊겨도 연결을 스스로 포기하지 않는다. 끊긴 뒤 원래 요청의 상태를 다시 조회하는 기능은 이미 있었지만, 연결이 **오류로 끝났을 때만** 동작했다. 조용히 죽은 연결은 오류를 내지 않는다.

신호가 45초 동안 없으면 웹이 그 연결을 끊고 원래 요청의 상태를 조회하게 했다.

- 접수 번호를 이미 받았으면 그 번호로 상태를 읽는다. 끝났으면 결과를 반영하고, 진행 중이면 계속 지켜본다.
- 접수 번호를 받기 전에 끊겼으면 원래 요청 키로 접수 여부를 묻는다. 접수되지 않았으면 다시 보낼지는 사용자가 고른다.
- 어느 경우든 조회만 한다. 재전송하지 않으므로 같은 지시가 두 번 실행되지 않는다.

AI 작업은 브라우저 연결과 무관하게 서버에서 계속 돈다. 그래서 포기하는 쪽이 안전하다.

## 의도치 않은 함정 — 가짜 시계 안에서 기다린 테스트

45초 감시의 테스트를 추가하자 테스트 실행이 끝나지 않았다. 웹 테스트 환경은 타이머를 가짜로 바꿔 둔다. 새 테스트는 45초가 지나기를 기다리는데, 가짜 시계는 누가 돌려 주지 않으면 흐르지 않는다. 멈춘 실행을 중단하고, 테스트가 시계를 직접 앞으로 돌리게 고쳤다.

작은 것도 하나 있었다. 로컬 화면의 버전(1.1.88)이 개발 서버(1.1.103)보다 낮았다. develop에 푸시할 때마다 CD가 패치 버전을 올리는데, 로컬 컨테이너는 닷새 전에 빌드한 이미지 그대로였다. `git pull`은 컨테이너를 바꾸지 않는다. 다시 빌드해 맞췄다.

토큰 사용량 화면의 가로 스크롤도 없앴다. 표에 최소 폭 440px이 걸려 있었고, 두 표를 나란히 둘지를 브라우저 창 폭으로 판단하고 있었다. 설정 화면은 옆 메뉴만큼 패널이 좁아서, 자리가 모자라도 나란히 놓였다.

## 마무리

- Keycloak 로그인 화면이 로컬과 개발 서버 모두 BATON 테마와 한국어로 나온다. 개발 서버는 테마 파일을 푸시하면 워크플로가 반영한다.
- 배포 중의 짧은 끊김은 일시 장애로 처리한다. 프로젝트 선택과 시작한 작업, 미저장 편집이 유지된다. 다시 로그인해도 직전 세션의 작업을 이어받는다.
- AI 진행 연결이 45초 동안 조용하면 웹이 끊고 원래 요청의 상태를 조회한다.

확인하지 못한 것이 많다. 배포 중 화면 유지는 테스트로만 확인했고, 실제 배포 중인 화면에서 본 것은 아니다. 수정본을 올린 그 배포는 옛 웹 코드가 받으므로 효과는 그다음 배포부터 나타난다. 45초 감시도 실제 화면에서 연결을 끊어 보지는 않았다.

다음에 볼 것은 이번 조사에서 나왔지만 범위에 넣지 않은 문제다. 배포 순간 돌고 있던 AI 요청은 서버가 다시 뜨면 "정리 대기"로 바뀌고, 그런 요청이 하나라도 있으면 새 AI 요청이 거부된다. 조사에서는 이 상태를 푸는 경로를 찾지 못했다. 생성 작업과 요구사항 정리에도 비슷한 문제가 보고됐다. 배포가 푸시마다 일어나는 지금은 이쪽이 더 급하다.
