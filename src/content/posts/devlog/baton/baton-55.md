> 이 글은 2026-11-23 하루의 기록이다. 오전에는 로컬 개발 서버가 배포 도메인 주소로 뜨는 문제를 고쳤고, 낮에는 Dependabot 알림을 닫았다. 오후에는 GitHub Actions가 결제 문제로 멈춘 것을 알게 됐고, 결제 대신 CD 전체를 개발 서버의 자체 러너로 옮겨 배포까지 마쳤다.

## 배경 — 로컬인데 배포 도메인 주소가 찍힌다

아침에 로컬에서 Vite를 띄우니 안내 주소에 `https://<배포 도메인>:5173/`이 함께 찍혔다. 그 도메인은 배포 서버용이다. 로컬 실행이 그 이름으로 바인딩되면 안 된다.

원인은 두 가지가 겹쳐 있었다.

1. `vite.config.ts`에 `host: true`가 있었다. dev 서버가 모든 인터페이스(`0.0.0.0`)에 바인드돼서, 다른 주소로 들어와도 응답할 수 있었다.
2. 로컬에서 쓰는 TLS 인증서의 SAN에 배포 도메인 이름이 들어 있다. Vite는 인증서에 적힌 이름을 "Local" 주소로 안내한다. 그래서 그 주소가 같이 찍혔다.

이 일을 시작으로, 이날은 "로컬 실행이 배포 환경을 보거나 배포 환경에 노출되지 않게 한다"는 정리가 API까지 이어졌다.

## 문제

1. 로컬 Vite와 API를 기본으로 loopback에만 묶으려면 어디를 바꿔야 하나. 컨테이너와 서버 배포는 그대로 두어야 한다.
2. main에 열린 Dependabot 알림 3건을 어떻게 닫나. develop은 이미 고친 버전을 쓰고 있다.
3. GitHub Actions가 결제 문제로 job을 시작조차 못 한다. 결제는 하지 않기로 했다. 그럼 배포는 어떻게 하나.
4. AI 지시 창에 스크롤 영역이 여러 개 생긴다.

## 결정 1 — 기본값은 localhost, 넓게 열 때만 변수로

Vite는 기본 바인드를 `localhost`로 바꿨다. 다른 PC에서 접속해야 할 때만 `BATON_DEV_HOST`(예: `0.0.0.0`)를 `deploy/local.env`에 넣는다.

인증서는 건드리지 않았다. 브라우저 신뢰 설정이 이 인증서에 묶여 있기 때문이다. 대신 Vite 출력에서 loopback 주소만 남기는 작은 플러그인을 넣었다. 재시작하니 `[::1]:5173`에서만 대기했고, 안내 주소도 `https://localhost:5173/` 하나만 나왔다.

수정을 마치고 보니 API에도 같은 문제가 두 겹으로 있었다.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| `BATON_ENV_PROFILE` 기본값 | 없음(`base.env`만 읽음) | `local` |
| `BATON_HOST` 기본값 | `0.0.0.0` | `localhost` |

프로필이 없으면 API는 `config/system/base.env`만 읽었다. 이 파일에는 Keycloak과 OAuth 콜백 주소가 배포 도메인으로 적혀 있다. 즉 로컬 API가 프로필 설정을 빠뜨리면 배포 서버의 Keycloak을 보고 있었다. Vite는 지정이 없으면 `local`을 쓰는데 API만 그렇지 않았다. `python -m server` 진입점에서 프로필이 없으면 `local`을 고르게 했다.

컨테이너가 이 기본값으로 빠지면 안 된다. API 이미지에는 `BATON_ENV_PROFILE=docker`를 명시했다. `BATON_HOST=0.0.0.0`은 Dockerfile에 이미 있어서 컨테이너 바인드는 그대로다.

확인은 두 단계로 했다. 먼저 `uvicorn.run`을 가짜로 바꿔 서버를 띄우지 않고 진입점이 고른 프로필과 Keycloak 주소만 봤다. 그다음 실행 중이던 API를 재시작해서 `127.0.0.1:8000`과 `[::1]:8000`에서만 대기하는 것을 확인했다. Vite 프록시를 거친 `/api/auth/config`도 200을 반환했다.

> 로컬 기본값은 "가장 좁게"가 맞다. 넓게 여는 쪽이 설정을 요구해야, 빠뜨렸을 때 사고가 나지 않는다.

## 결정 2 — 핫픽스는 main에만, develop에는 백머지로

Dependabot 알림 3건은 모두 개발 의존성이었다.

| 패키지 | main 버전 → 수정 |
| --- | --- |
| vite | 6.4.3 → 6.4.6 (medium 2건) |
| source-map-js | 1.2.1 → 1.2.4 (high 1건) |

develop은 이미 고친 버전을 쓰고 있어서 `npm audit`이 0건이었다. 그래서 main을 기준으로 `hotfix/web-dev-deps-security` 브랜치를 만들어 `package.json`과 lock 파일만 바꿨다. PR #31을 머지하자 알림 세 건이 모두 fixed로 닫혔다.

이후 main을 develop에 백머지했다. `package.json`과 lock 파일에서 충돌이 났다. `package.json`은 develop 쪽을 그대로 뒀다. vite `^6.4.6`과 browserslist override가 이미 있었기 때문이다. lock 파일은 develop 기준으로 두고 browserslist와 source-map-js만 main 버전 이상으로 올렸다.

여기서 한 가지 걸렸다. PR의 CI 체크가 전부 실패로 표시돼 있었다. 원인을 보니 코드가 아니라 GitHub Actions 결제 문제였다. job이 시작조차 못 하고 있었다. 머지 전 확인은 로컬 `npm run build`와 `npm audit`뿐이었다.

## 결정 3 — 결제 대신 CD 전체를 자체 러너로

저녁에 개발 서버 배포를 요청받고 CD를 수동으로 돌렸지만 첫 job에서 멈췄다. 실제 배포 job은 원래 개발 서버의 자체 러너(`baton-dev`)에서 돈다. 그런데 그 앞의 버전·배포 계획·품질 검사·이미지 빌드가 GitHub 호스팅 러너에서 돌았다. 호스팅 러너가 막히면 배포까지 가지 못한다.

GitHub 결제는 하지 않기로 했다. 그래서 CD의 모든 job을 자체 러너로 옮겼다.

- `cd.yml`의 호스팅 러너 job 4개와, 품질 검사가 재사용하는 `ci.yml`의 job 9개를 바꿨다.
- 러너는 저장소 변수 `BATON_CI_RUNNER`로 고른다. 기본값은 `["self-hosted","baton-dev"]`다.
- `ci.yml`에 `runner` 입력을 추가했다. CD가 부를 때만 자체 러너를 넘긴다. PR에서 따로 도는 CI는 여전히 `ubuntu-latest`다.
- 자체 Ubuntu 호스트에는 `python` 명령이 없을 수 있다. Python을 쓰는 job에 설치 단계를 명시했다.

```yaml
# cd.yml
runs-on: ${{ fromJSON(vars.BATON_CI_RUNNER || '["self-hosted","baton-dev"]') }}

# ci.yml (CD가 runner 입력을 넘길 때만 자체 러너)
runs-on: ${{ fromJSON(inputs.runner || '"ubuntu-latest"') }}
```

워크플로 변경은 develop에 올라가야 적용되므로 커밋하고 푸시했다. 푸시로 자동 실행된 CD가 `in_progress`로 바뀌었다. 자체 러너에서 job이 실제로 시작됐다는 뜻이다.

## 결정 4 — OS 패키지 레이어는 하루에 한 번 새로 만든다

첫 배포 시도는 버전·배포 계획·품질 검사 job 7개를 모두 통과했다. 실패한 곳은 이미지를 올리기 직전의 Trivy 스캔이었다.

| 이미지 | 걸린 것 |
| --- | --- |
| api, pipeline | krb5 계열 HIGH 56건 (`deb13u1` → `deb13u2`) |
| web | libxml2 HIGH 1건 (`r2` → `r3`) |

모두 수정 버전이 이미 나와 있었다. Dockerfile에도 OS 패키지 업그레이드 단계가 있었다. 그런데 빌드 캐시가 예전 업그레이드 레이어를 그대로 재사용해서, 업그레이드가 다시 실행되지 않았다.

캐시를 통째로 끄면 빌드가 느려진다. 그래서 업그레이드 레이어만 날마다 무효화하기로 했다.

```dockerfile
# BATON_OS_REFRESH changes daily in CI so a cached layer cannot keep yesterday's packages.
ARG BATON_OS_REFRESH=
RUN echo "OS refresh: ${BATON_OS_REFRESH}" && apt-get update && apt-get upgrade -y \
    && apt-get install -y --no-install-recommends \
    ...
```

CI는 빌드 직전에 `date -u +%Y-%m-%d`로 키를 만들어 `build-args`로 넘긴다. 값이 하루에 한 번 바뀌니 업그레이드 레이어는 하루에 한 번 다시 만들어지고, 그 뒤 레이어는 계속 캐시를 쓴다. 세 Dockerfile에 같은 방식을 넣었다.

다시 실행한 배포는 품질 검사, 보안 스캔, 이미지 게시, 배포까지 모두 자체 러너에서 통과했다. 배포 서버의 `/health`도 200을 반환했다. 배포된 버전은 1.1.90이고, 이날 커밋한 변경이 모두 들어갔다. private 저장소라 GHCR 저장 용량 한도도 걱정했는데, 이번에는 막히지 않았다.

> 보안 스캔이 "수정 버전이 있는 취약점"으로 실패하면 먼저 캐시를 의심한다. Dockerfile에 업그레이드 명령이 있다고 해서 매번 실행되는 것은 아니다.

## 결정 5 — AI 지시 창은 패널 하나만 스크롤한다

사이사이에 UI 문제 하나도 고쳤다. 우측 패널의 AI 지시 창에서 세 곳이 각자 스크롤되고 있었다. 패널 전체, 대화 목록, 펼친 "변경 대상" 영역이다. 하단 영역(변경안 적용, 추가 수정 지시, 새 지시)이 커지면 대화 목록이 100px까지 줄어든 채 스크롤되고, 동시에 바깥 패널도 스크롤됐다.

패널만 스크롤 영역으로 남겼다.

- 접힌 "변경 대상" 줄은 위에, 실행·적용 영역은 아래에 `sticky`로 붙인다. 그 사이의 대화만 움직인다.
- 패널 높이가 560px 이하이면 하단을 고정하지 않고 대화와 함께 흐르게 했다. 고정된 하단이 대화를 다 가리지 않게 하려는 것이다.
- 새 응답이 오면 맨 아래로 내리는 자동 스크롤 대상을 대화 목록에서 패널로 바꿨다.

질문·답변 모드는 원래 스크롤이 하나라 손대지 않았다.

Chrome 확장이 연결되지 않아 실제 앱에서는 보지 못했다. 같은 구조의 테스트 페이지를 headless Chrome으로 열어 확인했다. 패널 760px, 대화 12개, 변경 대상을 펼치고 대기 중인 변경안이 있는 상태에서, 수정 전에는 스크롤 영역 2개에 하단이 패널 밖으로 84px 밀려났다. 수정 후에는 스크롤 영역 1개에 하단이 패널 바닥에 붙었다.

## 의도치 않은 함정 — 2시간 34분짜리 테스트의 애매한 결과

API 변경을 확인하려고 전체 API 테스트를 백그라운드로 돌렸다. 2시간 34분이 걸렸고 결과는 8308개 통과, 147개 실패, 9개 오류였다.

이번 변경 때문은 아닐 가능성이 높다. 바꾼 `server/__main__.py`의 `main()`은 API를 실행할 때만 도는 진입점이고, 이 파일을 가져다 쓰는 테스트는 없다. 바인드와 TLS 관련 키워드로 고른 테스트 403개도 모두 통과했다.

문제는 근거가 깔끔하지 않다는 점이다. 출력은 마지막 몇 줄만 남아 실패 목록을 볼 수 없었다. 테스트가 도는 동안 다른 테스트 묶음을 동시에 돌렸고, 로컬 API도 재시작했다. 그 영향으로 실패했을 수도 있다. 정확히 가리려면 변경 전후 커밋에서 실패 목록을 뽑아 비교해야 하는데, 한 번에 2시간 반이 든다. 이번에는 그 비교를 하지 않고 넘어갔다.

브라우저 테스트도 비슷했다. `aiInstructionFlow.browser.cjs`에서 `.list`를 직접 스크롤하던 부분을 패널 스크롤로 고치고 "스크롤 영역은 하나" 검사를 추가했다. 그런데 이 테스트는 변경을 빼고 돌려도 `SOURCE_ERROR`로 실패해서 확인 근거가 되지 못했다.

## 마무리

이날 develop에 올린 변경은 모두 개발 서버에 배포됐다.

- 로컬 Vite와 API는 이제 기본으로 loopback에만 바인드되고, API도 기본으로 `local` 프로필을 읽는다.
- CD는 GitHub 결제 없이 개발 서버의 자체 러너에서 끝까지 돈다. 대신 CPU 2개짜리 서버 한 대라 품질 검사와 이미지 빌드가 순서대로 돌고, 그동안 서버에도 부하가 생긴다.

다음에 정할 것은 세 가지다. develop에 푸시할 때마다 `local` 대상 CD가 자동으로 돌아 러너를 차지하고, 등록된 `baton-local` 러너가 없어 배포 단계에서 멈춘다. 이날은 매번 손으로 취소했는데, 이 자동 실행을 끄거나 버전 올리기까지만 하게 바꿔야 한다. PR과 release/hotfix 브랜치의 CI도 자체 러너로 옮길지 정해야 한다. 마지막으로 전체 API 테스트의 실패 147개가 원래부터 있던 것인지 확인해야 한다.
