> 이 글은 2026-11-16 하루의 기록이다. 아침에는 버전 bump가 lock 파일을 놓치는 문제를 고쳤고, 오후에는 로컬 도커 주소를 정리했다. 저녁에는 두 달 넘게 실패하던 CD를 통과시켜 처음으로 서버에 배포했다.

## 배경 — 아침 푸시가 거부된 이유

하루는 커밋 하나를 푸시하다가 시작됐다. `uv.lock`에 적힌 두 워크스페이스 패키지 버전이 `VERSION`과 어긋나 있어서 그것만 맞추는 커밋이었다.

첫 푸시는 거부됐다. 그 사이 CD가 버전 bump 커밋을 하나 더 올려 둔 것이다. rebase한 뒤 lock의 버전을 다시 맞춰 올렸다.

같은 커밋을 손으로 반복하고 있다는 게 문제였다. CD의 bump 단계가 `VERSION`과 패키지 파일은 고치면서 `uv.lock`은 건드리지 않았다. 매번 사람이 따라가서 맞춰야 했다.

CD에는 더 큰 문제가 있었다. 로그를 보니 마지막으로 성공한 날이 9월 1일이었다. 그 뒤로 **83회 연속 실패**였다. 매 푸시마다 빨간 표시가 떴지만 배포 대상 서버가 없었으니 아무도 급하지 않았다.

## 문제

1. bump가 lock 파일까지 맞추게 하려면 CD에 무엇이 있어야 하나?
2. 로컬 도커는 어떤 주소로 띄워야 OAuth 로그인까지 되나?
3. CD는 어디서 멈추고 있었나? 고치면 어디까지 가나?
4. 배포할 서버가 생기면 무엇을 준비해야 하나?

## 결정 1 — lock 파일은 uv 없이 직접 고친다

`uv lock`을 돌리면 가장 깔끔하다. 그런데 CD의 bump 단계에는 uv가 설치돼 있지 않다. 버전 숫자 두 개를 고치려고 도구를 설치하는 것은 과하다고 봤다.

bump 스크립트에 `sync_uv_lock()`을 넣었다. 하는 일은 좁다.

- `uv.lock`에서 두 워크스페이스 패키지 항목의 `version`만 바꾼다. 외부 의존성 버전은 건드리지 않는다.
- 원래 줄바꿈 형식(CRLF/LF)을 유지한다.
- lock 파일은 있는데 두 패키지 중 하나라도 찾지 못하면 오류로 멈춘다. 조용히 넘어가면 같은 어긋남이 다시 생긴다.

CD 워크플로의 bump 커밋 `git add` 목록에 `uv.lock`을 넣었다. 버전 검사 스크립트도 lock의 두 버전을 `VERSION`과 비교하게 했다. 오늘 아침처럼 어긋나면 이제 CD의 계획 단계에서 바로 실패한다.

효과는 오후 푸시에서 확인됐다. CD가 만든 bump 커밋에 `uv.lock`이 다른 버전 파일들과 함께 들어 있었다.

## 결정 2 — 로컬은 `localhost`, 서버는 공개 도메인

오후에는 로컬 도커 배포를 `baton.localhost`라는 이름으로 패키징할 수 있는지 검토했다. HTTPS와 OAuth까지 포함해서다.

웹과 HTTPS, API의 Keycloak 연결은 모두 정상이었다. 막힌 곳은 Google 로그인이었다.

| 항목 | 결과 |
|---|---|
| 웹 HTTPS | 200, HTTP는 HTTPS로 리다이렉트 |
| Keycloak 설정 | issuer와 리다이렉트 등록 정상 |
| Google 로그인 | `*.localhost` 콜백 주소를 정책 위반으로 거부 |
| Keycloak 인증서 | 이 PC가 신뢰하지 않음 |

기본 로그인이 Google이라 사실상 로그인이 막힌 상태였다. 마침 회사 개발 서버의 공개 도메인을 정해 둔 참이라 역할을 나눴다. 공개 도메인은 서버용으로 두고, 로컬은 그냥 `localhost`를 쓴다.

바꾼 것은 이렇다.

- Caddy 사이트 이름을 `localhost`로 바꾸고, 80/443 포트는 `127.0.0.1`에만 묶었다.
- 브라우저와 토큰 issuer는 `https://localhost:8443`을 쓰고, API 컨테이너는 `https://keycloak:8443`으로 붙는다.

두 번째가 핵심이다. 컨테이너 안에서 `localhost`는 컨테이너 자신이다. 같은 주소를 API에도 주면 Keycloak을 찾지 못한다. 그래서 공개 주소와 내부 주소를 따로 두었다. Keycloak 인증서는 SAN에 `localhost`, `keycloak`, `127.0.0.1`을 넣어 다시 발급하고 Windows 신뢰 저장소에 등록했다.

남은 것은 Google과 Atlassian 콘솔에 새 콜백을 등록하는 일뿐이었다. 콘솔 작업은 직접 해야 한다.

같은 흐름에서 임시로 넣어 두었던 것들을 지웠다. 특정 프로젝트 전용 작업 폴더 변수, 9월에 한 번 쓰고 둔 점검 보고서 두 개, 예시 명령에 박혀 있던 개인 PC 경로다. 전용 변수는 기본값과 같은 경로를 가리키고 있어서 지워도 동작은 그대로였다.

## 결정 3 — CD를 막던 것을 하나씩 걷어 낸다

CD 실패 원인을 열어 보니 두 잡 모두 테스트는 통과했다. 보안 검사에서만 걸렸다.

| 잡 | 실패 원인 |
|---|---|
| Security Scan | Trivy 오설정 검사. Dockerfile 세 개 모두 `USER`가 없어 root로 실행 |
| API (Python 3.13) | pip-audit. 6개 패키지에서 취약점 31건 |

pip-audit는 3.13 매트릭스에서만 돌기 때문에 3.10 잡은 통과했다. 둘 다 고치기로 했다.

### 의존성 — 버전만 올리면 끝나지 않았다

`uv.lock`만 갱신했다. pyjwt, mcp, oauthlib, urllib3, pyasn1, certifi 여섯 개다. mcp는 2.x 메이저를 피해 1.x 안에서 올렸다.

문제는 pyjwt였다. 2.15는 운영 동작이 바뀌었다.

- JWKS를 다시 받는 동안 클라이언트 전체에 잠금을 잡는다. 그동안 캐시된 키로 하는 검증까지 최대 5초씩 멈춘다.
- 모르는 `kid`가 오면 30초 동안 다시 받지 않는다. 키가 교체된 직후 검증이 실패할 수 있다.

이 회귀를 잡은 것은 기존 동시성 테스트 13건이었다. 키 선택을 앱 쪽에서 직접 하도록 바꿔 이전 동작(잠금 없음, 짧은 쿨다운)을 유지했다.

> 보안 경고를 없애려고 올린 버전이 인증 경로를 느리게 만들 뻔했다. 테스트가 없었다면 운영에서 알았을 것이다.

### non-root — 세 이미지가 각자 다른 이유로 어려웠다

- **pipeline**: 일반 사용자 하나를 추가하면 끝이었다.
- **web**: 비특권 nginx 이미지로 바꿨다. 컨테이너 내부 포트가 80에서 8080으로 바뀌어 compose 포트, Caddy 설정, 헬스체크를 같이 고쳤다.
- **api**: 손이 가장 많이 갔다. CLI 설정 폴더를 `/root/...` 경로로 마운트하고 있었고, SSH 키를 복사해 권한을 고치는 로직도 root를 전제로 했다.

api와 pipeline은 uid 10001로 돈다. 홈 경로를 바꾸고, SSH 키를 찾을 때는 passwd의 홈을 보게 했다. 배포 스크립트에는 소유권을 맞추는 단계를 넣었다. API 이미지로 root 컨테이너를 한 번 띄워 작업 폴더 소유자를 런타임 uid로 바꾼다.

Docker Desktop은 바인드 마운트 권한이 달라서 로컬 Windows에서는 `BATON_UID=0`을 줘야 한다. 이 값은 git에 올리지 않는 `.env`에 둔다.

로컬에서 pip-audit 0건, Trivy 오설정 0건, 관련 테스트 1,254건이 통과했다. API 전체 테스트는 한 시간을 넘길 것 같아 중간에 멈췄다.

### 다음 벽 — 한 번도 와 보지 않은 단계

푸시하자 두 원인은 9월 이후 처음으로 통과했다. 그런데 바로 다음 단계인 이미지 발행에서 세 이미지가 모두 걸렸다. 발행 전 이미지 스캔이었다.

원래 있던 문제다. 앞 단계에서 늘 멈췄기 때문에 이 단계까지 온 적이 없었을 뿐이다. 수정판이 나온 HIGH·CRITICAL 취약점은 앱 코드가 아니라 주변에 있었다.

- 고정해 둔 베이스 이미지의 OS 패키지 (openssl, zlib, brotli 등)
- 시스템 `pip`에 동봉된 라이브러리와 빌드할 때만 쓰는 uv
- api 이미지의 `npm` 자체에 동봉된 라이브러리

빌드할 때 OS 보안 업데이트를 적용하고, 빌드가 끝나면 런타임에 쓰지 않는 uv·pip·npm을 지웠다. 다음 실행에서 품질 게이트, 이미지 발행, 다이제스트 검증까지 모두 통과했다.

## 결정 4 — 배포 잡이 기다리던 러너를 만든다

마지막 배포 잡은 대기 상태에서 움직이지 않았다. 이 잡은 self-hosted 러너에서만 도는데, 저장소에 등록된 러너가 한 대도 없었다. 그대로 두면 GitHub이 24시간 뒤에 취소한다.

배포 스크립트가 bash이고 `/`로 시작하는 경로를 쓰니 Linux 호스트가 맞았다. 클라우드 VM 한 대를 회사 개발 서버로 쓰기로 하고 러너를 설치했다.

- Docker Engine과 Compose 플러그인을 공식 apt 저장소에서 설치했다.
- 러너 전용 계정을 만들고 docker 그룹에만 넣었다. sudo 권한은 주지 않았다.
- 러너 바이너리는 SHA-256을 확인하고 systemd 서비스로 띄웠다.

설치에 필요한 sudo는 임시 파일 하나로 열었다가 작업 직후 지웠다. 지운 뒤 sudo가 비밀번호를 요구하는 것까지 확인했다.

디스크가 문제였다. 설치 후 여유가 3GB였는데 api 이미지만 2GB다. 볼륨을 30GB로 늘리고 재부팅하자 cloud-init이 파티션과 파일시스템을 자동으로 늘려 두었다. 따로 할 작업이 없었다.

서버 설정 파일은 로컬 사본을 바탕으로 만들었다. Keycloak 주소와 OAuth 콜백을 공개 도메인으로 바꾸고, 프로젝트별 작업 폴더 경로를 컨테이너 기준으로 고치고, 프록시 뒤에서 도는 설정을 켰다. Caddy가 443은 웹으로, 8443은 Keycloak으로 넘기고 인증서는 Let's Encrypt에서 자동으로 받는다. Keycloak realm은 로컬 것을 그대로 옮겼다.

산출물 저장소에 쓰기 위한 키도 필요했다. GitHub 쪽은 쓰기 가능한 deploy key로 등록하고 서버에서 접근되는 것을 확인했다. Bitbucket 쪽은 저장소별 access key가 읽기 전용이라 맞지 않는다. 쓰기 권한 있는 계정에 직접 등록해야 해서 남겨 두었다.

## 의도치 않은 함정 — umask 027이 API를 재시작시켰다

첫 배포는 실패했다. API 컨테이너가 계속 재시작했다.

설정 파일을 서버에 넣을 때 umask 027을 썼다. 그래서 `config/`는 러너 계정만 읽을 수 있었다. 그런데 API는 이제 root가 아니라 uid 10001로 돈다. 설정을 읽지 못하고 죽는 것이었다.

non-root로 바꾸는 날에만 생길 수 있는 실패다. root로 돌던 시절에는 파일 권한을 아무리 좁혀도 읽혔다.

서버의 `config/`를 실행 그룹이 읽을 수 있게 바꾸고 실패한 잡만 다시 돌려 성공했다. 재발을 막으려고 배포 스크립트의 소유권 단계가 매번 `config/`의 그룹과 권한을 맞추게 했다. 다른 사용자 권한은 계속 막는다.

같이 고친 것이 하나 더 있다. 데이터 스냅샷 도구가 컨테이너가 없을 때 나오는 메시지로 "멈춘 상태"를 판단하는데, Docker 29는 그 메시지를 소문자로 바꿨다. 대소문자를 무시하게 했다.

## 마무리

- CD가 두 달 넘게 빨간색이어도 아무도 급하지 않았던 이유는 배포 대상이 없었기 때문이다. 대상이 생기자 그동안 가려져 있던 단계가 하나씩 드러났다. 보안 검사, 이미지 스캔, 러너, 권한 순서였다.
- non-root 전환은 Dockerfile 한 줄로 끝나지 않는다. 포트, 마운트 경로, 홈 디렉터리, 배포 스크립트의 파일 권한까지 root를 전제로 한 곳을 모두 찾아야 한다.

확인하지 못한 것도 적어 둔다. 서버에서 Jira와 Google 연동은 OAuth 저장소 초기화가 남아 있어 아직 쓸 수 없다. 사내 네트워크에서는 공개 도메인이 아직 옛 내부 주소로 연결된다. CI는 Python 테스트를 돌리지 않고 설치와 감사만 한다. 빌드에 쓰는 uv 버전에도 권고가 있지만 게이트에 걸리지 않아 그대로 두었다.

러너 라벨을 서버용으로 바꾸면서 develop 브랜치의 로컬 배포 잡은 받을 러너가 없어졌다. 서버에는 main에 반영될 때 배포된다. 다음에 할 일은 서버의 OAuth 저장소 초기화, Bitbucket 쓰기 키 등록, 그리고 develop 배포 채널을 어떻게 둘지 정하는 것이다.
