> 이 글은 2026-11-19 하루의 기록이다. 저녁 무렵 서버의 Keycloak 설정을 살펴보다가 로컬 구성 두 벌을 하나로 합쳤고, 서버의 Google 로그인 오류 원인을 찾았다. 그 뒤로는 물리 데이터 화면의 관계선과 속성 창을 고쳤다.

## 배경 — 지난 일지가 남긴 숙제

#53은 "로컬 Keycloak 구성 두 벌을 하나로 합친다"를 다음 할 일로 적고 끝났다. 하루는 그 근처에서 시작됐다. 먼저 서버의 Keycloak이 어떻게 떠 있는지부터 확인했다.

서버의 Keycloak은 BATON 앱과 별도의 Compose 프로젝트다. 저장소의 `deploy/keycloak/docker-compose.yml`과 같은 파일에, 서버에만 있는 override 하나를 더 얹는다. 이 override가 Keycloak 자체 TLS를 끄고 포트를 loopback 8080에만 연다. TLS는 앞단 Caddy가 끝내고 내부 네트워크로 넘긴다.

서버 구성은 정상이었다. 문제는 로컬이었다. 로컬에는 overlay가 두 개 있었다.

| 파일 | 구성 |
| --- | --- |
| `compose.keycloak.yaml` | HTTP 18080, PostgreSQL 번들 |
| `compose.keycloak.existing.yaml` | HTTPS 8443, `start-dev`, 기존 볼륨 재사용 |

## 문제

1. 두 overlay 중 어느 쪽을 기준으로 합칠까. 볼륨이 이미 있는 경우와 없는 경우를 파일 하나로 처리할 수 있나.
2. 서버에서 Google 로그인 시 "401 오류: deleted_client"가 난다. BATON 로그에는 아무것도 없다.
3. 물리 데이터 모델의 관계선이 ERD 표기 관례와 다르다. 선 위에 `1 : 0..N` 같은 글자가 붙고 끝에는 화살표가 있다.
4. 물리 데이터의 속성 창이 공간을 많이 차지한다. 필드 하나를 보려고 스크롤을 한참 내려야 한다.

## 결정 1 — 실제로 쓰던 쪽을 기준으로 합친다

기준은 existing 쪽으로 정했다. 실제로 매일 쓰던 구성이고, 보호된 API는 Keycloak을 HTTPS 엔드포인트로 요구한다. 옛 `compose.keycloak.yaml`의 HTTP 18080 구성은 이 요구를 만족하지 못한다.

두 파일이 갈라진 이유는 볼륨 하나였다. existing 쪽은 볼륨을 `external: true`로 선언해서, 볼륨이 없으면 아예 뜨지 않았다. 이 줄을 빼고 이름만 변수로 받게 했다.

```yaml
volumes:
  keycloak_data:
    name: ${KC_DATA_VOLUME:-keycloak_data}
```

이제 볼륨이 있으면 realm·클라이언트·사용자를 그대로 쓴다. Compose가 만든 볼륨이 아니라는 경고가 나오지만 동작에는 문제가 없다. 볼륨이 없으면 빈 볼륨을 만들고, 첫 기동 때 bootstrap 관리자 계정을 셸 환경 변수로 넘기면 된다.

대신 새로 띄우는 사람은 인증서가 먼저 있어야 한다. `localhost`, `127.0.0.1`, `keycloak`을 모두 담은 인증서를 `work/deploy/keycloak/tls/`에 두어야 하고, 만드는 명령을 README에 넣었다. API는 컨테이너 안에서 `https://keycloak:8443`으로 접속하면서 이 인증서로 검증한다.

existing 파일과 PostgreSQL 번들 전용 env 예시 파일은 지웠다. CI의 Keycloak 구성 검증 단계도 더 이상 `--env-file`을 넘기지 않는다. 로컬 `.env`의 `COMPOSE_FILE`은 `compose.yaml:compose.local.yaml:compose.keycloak.yaml` 세 개가 됐다.

## 결정 2 — `deleted_client`는 BATON이 아니라 Google 쪽 문제였다

서버의 Google 로그인 흐름은 BATON → Keycloak → Google 순서다. Keycloak의 Google IdP가 사용자를 Google로 넘기는 순간 Google이 오류를 낸다. 그래서 BATON 서버에도 Keycloak 로그에도 남지 않았다.

서버에는 Google OAuth 클라이언트가 두 개 있었다. 같은 Google 프로젝트에 속한, 용도가 다른 클라이언트다. 각각 Google에 인증 요청을 보내 응답을 비교했다.

| 용도 | Google 응답 |
| --- | --- |
| Keycloak의 Google 로그인(IdP) | `deleted_client` |
| BATON의 Drive·Sheets 연동(#53에서 업로드) | `redirect_uri_mismatch` |

두 번째 응답은 오류처럼 보이지만 반대로 읽어야 한다. Keycloak 콜백 주소로 시험했으니 등록되지 않은 주소라는 답이 나온 것이고, 클라이언트 자체는 살아 있다는 뜻이다. 죽은 쪽은 로그인용 클라이언트였다. Google Cloud에서 삭제된 상태였다.

해결은 Google Cloud Console에서 해야 한다. 두 가지 방법을 정리해 두었다.

- 웹 애플리케이션 클라이언트를 새로 만들고, Keycloak 브로커 콜백(`/realms/baton/broker/google/endpoint`)을 리디렉션 URI로 등록한다. 그다음 Keycloak 관리 콘솔의 Google IdP에 새 ID와 Secret을 넣는다.
- 살아 있는 Drive용 클라이언트에 콜백 주소를 추가해 함께 쓴다. 클라이언트는 하나로 줄지만 로그인과 Drive 연동이 한 클라이언트에 묶인다.

로그를 보다가 오전에 Keycloak 관리 콘솔 로그인 실패가 여러 번 있었던 것도 찾았다. 비밀번호 불일치와 없는 사용자였다. bootstrap 관리자 비밀번호는 첫 기동 때만 쓰이니, `server.env`에 적힌 값과 실제 값이 달라졌을 수 있다. 콘솔에 들어갈 수 없다면 Keycloak을 잠시 멈추고 `kc.sh bootstrap-admin`으로 임시 관리자를 만들어야 한다.

> 오류 메시지가 BATON 화면에 떠도 원인이 BATON에 있다는 보장은 없다. 로그가 비어 있다는 것 자체가 "요청이 여기까지 오지 않았다"는 단서였다.

## 결정 3 — 관계선은 IE 표기(까마귀발)로 그린다

여기서부터는 "별도 요청 전까지는 로컬에서 반영하고 테스트한 뒤 배포한다"는 방침으로 진행했다.

ERD의 표준 표기 중 가장 흔한 IE 표기를 골랐다. 선 끝의 기호 두 개로 카디널리티를 나타낸다.

| 위치 | 기호 | 의미 |
| --- | --- | --- |
| 엔티티 바로 옆 | 세로줄 / 까마귀발 | 최대 하나 / 여러 개 |
| 그 바깥 | 세로줄 / 원 | 필수 / 선택 |

이 조합으로 `1`, `0..1`, `1..N`, `0..N` 네 가지가 된다. 화살표는 없앴다. 대신 선 모양으로 관계 종류를 구분한다. 실선은 식별 관계, 점선은 비식별 관계다.

저장 형식은 바꾸지 않았다. 기존 데이터에는 PlantUML 토큰(`||`, `o{`)과 UML 범위(`1`, `0..*`)가 섞여 있다. 표기 규칙을 `erdNotation.ts`에 모아 두 형식을 모두 읽어 네 가지 끝 모양 중 하나로 바꾸게 했다. 카디널리티가 없는 외래키는 자식 쪽 `0..N`, 부모 쪽 `1`로 본다.

기호는 SVG 마커로 그렸다. `orient="auto-start-reverse"`를 쓰면 마커 하나를 선의 시작과 끝에 모두 붙일 수 있다. 방향은 브라우저가 알아서 뒤집는다.

선 위의 글자는 관계 이름만 남겼다. 유형과 카디널리티는 마우스를 올렸을 때 나오는 설명과 화면 읽기 프로그램용 설명으로 옮겼다. `parent_id · 식별 관계 · 1 : 0..N` 같은 식이다.

관계 편집 화면도 같이 바꿨다.

- 식별/비식별을 고르는 "관계 유형" 항목을 넣었다. 값은 기존 `style` 필드에 저장한다.
- 카디널리티 선택지에 "0..N · 없거나 여러 개"처럼 설명을 붙였다.
- 고르는 즉시 "출발 데이터 ─기호─ 도착 데이터" 미리보기가 바뀐다.

새 관계의 기본값은 출발 `1`, 도착 `0..N`, 실선이다. 기존 관계가 모두 실선으로 그려져 있어서 맞췄는데, 실제로는 비식별 관계가 더 흔하다. 기본값을 점선으로 바꿀지는 아직 정하지 않았다.

## 결정 4 — 속성 창은 너비를 끌어서 바꾸고, 필드는 표로 본다

속성 창은 너비가 고정이었다. 그 안에서 라벨이 입력칸 위에 한 줄씩 쌓였고, 필드는 이름만 보이는 접힌 카드 목록이었다. 필드 14개짜리 데이터 하나를 보려면 스크롤을 한참 내려야 했다.

먼저 너비를 사용자에게 넘겼다. 속성 창 왼쪽 가장자리에 `role="separator"` 손잡이를 두고, 끌면 작업 영역 grid의 CSS 변수 `--inspector-width`가 바뀐다.

- 키보드로는 ←/→ 24px씩, Shift를 누르면 4배로 움직인다.
- 더블클릭이나 Home 키로 기본 너비로 돌아간다.
- 정한 너비는 localStorage에 물리 데이터와 논리 데이터를 따로 기억한다.
- 다이어그램은 최소 320px를 남긴다.

다음은 기본 정보다. 라벨을 입력칸 왼쪽에 두는 속성표 형태로 바꿨다. 속성 하나가 두 줄에서 한 줄이 되니 세로 길이가 절반쯤으로 줄었다. 창을 700px 넘게 넓히면 container query가 짧은 속성을 2열로 배치한다. 설명처럼 긴 글은 한 줄을 다 쓴다.

필드는 표로 바꿨다. 한 줄에 `#`, 필드명/물리명, 타입(길이), 키, NULL이 보인다. PK와 FK는 색이 다른 배지로, NULL을 허용하지 않는 필드는 `NOT NULL`로 강조했다. 위쪽 검색칸으로 이름과 타입을 바로 거를 수 있다.

행을 누르면 그 아래에 전체 속성 편집칸이 펼쳐진다. 필드마다 크게 붙어 있던 빨간 삭제 버튼도 이 안으로 옮겼다. 다른 화면에서 특정 필드로 이동해 오면 그 행이 자동으로 펼쳐지게 했다. 접힌 행으로 점프하면 아무것도 안 보이는 문제가 생기기 때문이다.

새 필드 표 테스트를 쓰다가 버그 하나를 찾았다. 읽기 전용일 때도 빈 목록 안내에 "[필드 추가]로 시작하세요"가 나오고 있었다.

## 의도치 않은 함정 — 대소문자만 다른 파일 두 개

ERD 작업 초반에 표기 규칙 파일 `erdNotation.ts`와 기호 컴포넌트 `ErdNotation.tsx`를 만들었다. 그리고 잘못 만든 `erdNotation.tsx`를 지웠다.

Windows 파일 시스템은 대소문자를 구분하지 않는다. `erdNotation.tsx`를 지우는 명령이 방금 만든 `ErdNotation.tsx`를 지웠다. 컴포넌트 파일 이름을 `ErdSymbols.tsx`로 바꿔 다시 만들었다.

속성표 CSS에서도 한 번 걸렸다. 공용 폼의 `.field.c6 { grid-column: span 6 }` 규칙이 새 2열 grid 안에서 암묵적인 열을 만들어 배치를 깨뜨렸다. 속성표 안에서는 `grid-column: auto`로 덮었다. 예전 규칙인 `label { flex-direction: column }`도 라벨을 다시 세로로 쌓고 있어서 함께 덮었다.

## 마무리

이날 바꾼 것은 모두 로컬에만 있다. Keycloak overlay 통합, ERD 표기, 속성 창 개선이 커밋되지 않은 채 한 작업 트리에 쌓여 있다.

- 화면 확인은 Chrome 확장이 연결되지 않아 esbuild로 묶은 미리보기 화면을 headless Chrome으로 캡처하는 방식으로 했다. 실제 데이터와 라이트·다크 테마로 확인했지만, 로그인한 실제 앱 화면에서는 아직 보지 못했다.
- 웹 단위 테스트는 3637개 모두 통과했고 타입 검사도 통과했다. 선 위에 카디널리티 글자를 쓰지 않게 바뀐 동작에 맞춰 기존 테스트 2개를 고쳤다.

다음에 할 일은 세 가지다. 로그인한 화면에서 두 UI 변경을 확인한 뒤 커밋하고 배포한다. Google Cloud에서 로그인용 OAuth 클라이언트를 다시 만들어 Keycloak IdP에 넣는다. 새 관계의 기본 선 모양을 정한다.
