> 이 글은 2026-11-17 하루의 기록이다. 오전에는 서버의 OAuth 저장소를 초기화했고, 오후 내내 Google 연동을 붙였다. 저녁에는 AI API 키 설정을 넣고 compose 파일을 정리했다.

## 배경 — 지난 일지가 남긴 숙제

#52는 "서버의 OAuth 저장소 초기화가 남아 있다"로 끝났다. 하루는 정확히 그 오류로 시작됐다. 서버에서 Jira 연결을 누르면 "승인 상태 저장소의 초기화 또는 복구가 필요합니다"가 떴다.

상태를 찍어 보니 `{"jira": "missing", "google": "no-client"}`였다. API 로그에는 `POST /api/jira/oauth/connect`가 409로 거절된 기록이 쌓여 있었다.

이 저장소는 API가 켜질 때 자동으로 만들어지지 않는다. 기존 암호화 키나 자격을 실수로 덮어쓰지 않으려고 일부러 그렇게 설계했다. 만드는 방법은 로그인한 관리자의 액세스 토큰을 들고 서버에서 CLI(`oauth_setup initialize`)를 한 번 실행하는 것뿐이었다.

## 문제

1. 관리자 토큰을 브라우저에서 꺼내 SSH로 서버까지 옮기는 절차가 꼭 필요한가.
2. Google 연동은 서버용 OAuth 클라이언트 파일이 없다. 이 파일을 서버에 어떻게 넣을까.
3. Google 승인 후 돌아오면 연결이 안 돼 있고, 팝업도 제대로 닫히지 않는다. 원인은 어디인가.
4. 서버에는 Claude·Codex 로그인이 없다. AI 기능을 어떻게 쓰게 할까.

## 결정 1 — 저장소 초기화는 관리자 API로 한다

처음 준비한 방법은 스크립트였다. 콘솔에서 토큰을 클립보드로 복사하면 스크립트가 SSH 표준입력으로 서버에 넘기고 클립보드를 비운다. 토큰이 명령 기록에 남지 않게 하려는 것이었다.

"왜 이걸 실행해야 하냐"는 질문을 받고 다시 생각했다. 필요한 건 관리자 권한으로 `initialize`를 한 번 부르는 것이다. 이미 `/api/admin/*` 경로가 여럿 있고 모두 같은 관리자 확인을 거친다. HTTP 경로로 노출해도 같은 토큰을 같은 검증기로 확인하니 위험이 새로 생기지는 않는다.

| 경로 | 동작 |
| --- | --- |
| `GET /api/admin/oauth-stores` | `missing` / `ready` / `unusable` / `no-client` 조회 |
| `POST /api/admin/oauth-stores/initialize` | 없는 저장소만 만든다. 이상한 상태면 409 |

`initialize`는 원래 멱등이다. 없는 저장소만 만들고 있는 저장소는 건드리지 않는다. 버튼을 여러 번 눌러도 기존 자격이 지워지지 않는다.

옛 JSON 저장소를 가져오는 이전 작업만은 CLI 전용으로 남겼다. 쓰기를 멈추고 백업한 뒤 해야 하는 일이라 버튼 하나로 끝낼 성격이 아니다.

설정 › 시스템 › 진단에 "OAuth 저장소" 패널을 붙이고 배포했다. [초기화]를 누르자 `jira: ready`가 됐고, 곧바로 Jira 연결도 성공했다.

> 운영자가 토큰을 손으로 나르는 절차는 보안 장치가 아니라 그냥 불편함이었다. 권한 확인이 같다면 화면의 버튼이 더 안전하다.

## 결정 2 — Google 클라이언트는 설정 화면에서 올린다

Google은 서버용 웹 애플리케이션 OAuth 클라이언트가 있어야 한다. 환경 변수 `GOOGLE_OAUTH_CLIENT`로 경로를 지정하는 방법만 있었는데, 서버에 파일을 넣으려면 또 SSH가 필요하다.

그래서 업로드를 받게 했다. 서버는 파일을 받으면 세 가지를 확인한다.

- 유형이 '웹 애플리케이션'인가. 데스크톱 유형이면 이유를 알려 주며 거절한다.
- 필수 항목이 있는가.
- 서버의 콜백 주소가 리디렉션 URI에 등록돼 있는가.

통과하면 영구 볼륨에 0600 권한으로 쓰고 Google 저장소까지 바로 초기화한다. 이미 초기화된 뒤 다른 파일로 바꾸려는 업로드는 409로 거절한다. 저장소가 초기화 시점의 클라이언트에 묶여 있기 때문이다. 환경 변수가 지정된 서버라면 그 값이 우선이고 업로드 영역은 보이지 않는다.

로컬에 있던 클라이언트 파일은 `installed` 유형에 리디렉션 URI가 `http://localhost` 하나뿐인 데스크톱용이었다. 올렸다면 바로 이 검증에 걸렸을 것이다. 웹 애플리케이션 클라이언트를 새로 만들어 올렸다.

같이 화면도 바꿨다. "Google 연동"을 별도 메뉴에서 빼서 외부 연동의 카드 하나로 넣었다. 처음에는 다단 배치로 공간을 꽉 채웠는데, 결국 1열로 정리했다. 카드가 넓어진 만큼 입력 필드를 가로로 나란히 놓았다.

## 결정 3 — PKCE 값은 저장하지 않고 다시 계산한다

업로드한 클라이언트로 연결을 눌렀다. 두 가지가 이상했다.

- 승인하러 갈 때 "변경사항이 저장되지 않을 수 있습니다" 경고가 뜬다.
- 승인을 마치고 돌아오면 여전히 미연결이다.

두 번째부터 봤다. 서버 로그에 `/api/google/callback`이 400으로 실패해 있었다. Google 라이브러리는 승인 요청을 만들 때 무작위 PKCE verifier를 생성한다. 그런데 콜백을 처리할 때는 Flow 객체를 새로 만들어서 그 값이 없다. Google은 verifier가 없는 토큰 교환을 거절한다.

verifier를 세션에 저장하는 대신 계산하게 했다. state는 서버가 직접 만들고, verifier는 클라이언트 비밀값과 state로 만든 HMAC이다.

```python
def _code_verifier(secret: Path, state: str) -> str:
    document = json.loads(secret.read_text(encoding="utf-8"))
    client_secret = next(iter(document.values()))["client_secret"]
    digest = hmac.new(client_secret.encode("utf-8"), b"baton-google-pkce:" + state.encode("utf-8"),
                      hashlib.sha256).digest()
    return base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")
```

승인 요청과 콜백에서 같은 입력이 들어오니 같은 값이 나온다. 저장소도 만료 처리도 필요 없다.

교환 단계에서 하나 더 막았다. Google이 예전에 받은 권한(openid, email)을 같이 돌려주면 라이브러리가 "범위가 바뀌었다"며 거절할 수 있다. 추가 범위는 허용하고, 대신 BATON이 쓰는 Drive·Sheets 권한이 들어 있는지 직접 확인한다.

첫 번째 경고는 현재 창 자체를 승인 페이지로 이동시켜서 생긴 것이었다. Jira처럼 팝업으로 승인하게 바꿨다.

## 결정 4 — 팝업은 `window.opener`를 믿지 않는다

팝업으로 바꾸자 연결은 됐다. 그런데 승인을 마친 팝업이 닫히지 않고 그 안에서 BATON 전체를 다시 띄웠다.

원인은 Google 승인 화면의 Cross-Origin-Opener-Policy로 추정했다. 다른 출처를 거치면 팝업과 원래 창의 연결인 `window.opener`가 끊긴다. 그러면 양쪽 모두 상대를 잃는다.

- 팝업은 원래 창이 있는지 몰라 스스로 닫지 못한다.
- 원래 창은 팝업이 열려 있는데도 닫힌 것으로 보고 대기를 멈춘다.

창 핸들 대신 다른 신호를 쓰게 했다.

| 쪽 | 이전 | 이후 |
| --- | --- | --- |
| 팝업 | `opener`에 결과 전달 | BroadcastChannel로 같은 출처 창에 알림 |
| 원래 창 | 팝업 `closed` 감시 | 채널 알림 + 3초마다 상태 조회, 최대 10분 |

이렇게 해도 팝업 안에서 앱이 한 번 더 뜨는 현상은 남았다. 연결이 끊긴 뒤에는 브라우저가 팝업의 `window.close()`도 막는 것으로 보였다. 닫기에 실패하면 설정 화면을 띄우게 해 둔 것이 앱 전체를 다시 띄운 셈이었다.

마지막 수정은 팝업으로 돌아왔을 때 앱 대신 작은 결과 화면만 그리는 것이다. 결과를 알리고 닫기를 시도하고, 막히면 "이 창은 닫아도 됩니다"만 남는다. 앱을 띄우지 않으니 로그인 확인이나 프로젝트 조회 같은 요청도 생기지 않는다.

연결할 때 계정 이메일도 저장하게 했다. Google이 돌려주는 자격 정보에는 계정이 없어서 카드에 아무것도 표시되지 않았다. 이미 받은 Drive 권한으로 `about` API를 불러 이메일을 얻는다. 새 권한을 요청하지 않으니 승인 화면도 그대로다.

## 결정 5 — AI 키는 공급자 바로 아래에 둔다

Google 연결이 확인된 뒤로는 서버 배포를 멈추고 로컬에서 개발하기로 했다. 다음 과제는 AI였다. 서버에는 CLI 로그인이 없어서 API 키가 있어야 AI 기능이 동작한다.

키는 외부 연동 토큰과 같은 암호화 저장소에 AI 전용 항목으로 넣었다. 우선순위는 저장한 키, 프로세스 환경 변수, env 파일 순이다. 재시작 없이 다음 요청부터 쓰인다. 지금까지 환경 변수만 보던 Claude CLI 실행에도 저장한 키를 넘기게 했다.

처음에는 AI 설정 맨 아래에 "API 키 인증" 섹션을 따로 만들었다. 공급자를 고르는 곳과 키를 넣는 곳이 떨어져 있다는 지적을 받고 옮겼다. 이제 백엔드와 공급자를 고르면 바로 아래에 그 조합에 필요한 키만 보인다. 나머지 키는 접어 둔다.

[연결 확인] 버튼도 넣었다. 실제 AI 요청과 같은 경로로 짧은 질문을 한 번 보내고, 성공하면 공급자·모델·걸린 시간을 보여 준다. 캐시는 우회한다. 실패하면 키 거부, 한도 초과, 모델 없음 같은 원인의 종류만 보여 준다. 공급자의 원문 오류에는 키나 내부 경로가 섞일 수 있어서다.

## 의도치 않은 함정 — 수동 배포가 push CD에 취소됐다

이날 서버 수동 배포를 열 번 돌렸다. 그중 하나가 품질 게이트 단계에서 이유 없이 취소됐다.

품질 게이트(`ci.yml`)는 CD가 재사용하는 워크플로인데, 동시 실행 그룹이 브랜치 기준이었다. 같은 develop에서 도는 수동 배포와 push로 시작된 CD가 같은 그룹이 됐고, 나중에 시작한 쪽이 먼저 것을 취소했다. 그전에는 push 쪽이 취소돼서 드러나지 않았다.

처음에는 이벤트 이름으로 그룹을 나누려 했다. 그러면 채널만 다른 수동 배포 두 개는 여전히 서로 취소한다. 그래서 CD 안에서 불릴 때는 실행 ID로 그룹을 잡았다.

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.workflow == 'CI' && github.ref || github.run_id }}
```

CI 단독 실행은 지금처럼 같은 브랜치의 이전 실행을 취소한다. 다음 배포에서 push 실행과 겹쳤는데도 둘 다 끝까지 갔다.

## 마무리 — compose 정리

하루를 정리하면서 루트의 compose 파일도 줄였다. 내용이 같던 개발·운영 서버용 파일을 `compose.server.yaml` 하나로 합쳤다. 로컬은 프록시 설정 파일까지 `compose.local.yaml` 안에 내장했고, `.env`에 `COMPOSE_FILE`을 넣어 `docker compose up -d --wait`만으로 로컬 스택이 뜨게 했다. 9개가 7개가 됐다.

이 구성으로 서버에 배포해 API·Web 포트가 loopback에만 열린 것을 확인했다. 옛 서버용 파일은 롤백 대비로 서버에 남겨 두었다.

- 이날 Google 연동에서 고친 버그는 모두 "한 번의 요청 안에서 끝나지 않는 흐름"에서 나왔다. 승인 요청과 콜백, 원래 창과 팝업처럼 두 지점이 상태를 나눠 가질 때는 저장하거나 전달하기보다 양쪽에서 다시 계산하거나 서버에 물어보는 쪽이 덜 깨진다.
- 수동 배포가 잦아지자 숨어 있던 동시 실행 설정 문제가 드러났다. #52처럼 배포 대상이 생기면 그동안 안 보이던 것이 하나씩 나온다.

확인하지 못한 것도 적어 둔다. 로컬에서 API 전체 테스트를 3시간 44분 돌렸는데 139건이 실패했다. JWKS 테스트 하나는 이전 커밋에서 깨뜨린 것이라 고쳤다. 나머지는 대부분 Git 프로세스 정리를 다루는 테스트라 Windows 환경 문제로 보이지만, 변경 전 코드와 비교하던 작업을 임시 파일 정리와 함께 지워서 확인하지 못했다. CI는 여전히 Python 테스트를 돌리지 않는다.

다음에 할 일은 compose를 7개에서 4개로 더 줄이는 것이다. 기본 포트를 loopback으로 바꿔 서버용 파일을 없애고, 쓰지 않는 AI 로그인 공유 파일을 지우고, 로컬 Keycloak 구성 두 벌을 하나로 합친다.
