> 이 글은 2026-11-24 하루의 기록이다. 전날 CD를 개발 서버의 자체 러너로 옮겼고, 이날은 그 뒤처리를 했다. develop 푸시의 동작을 하루에 두 번 바꿨고, PR CI까지 자체 러너로 옮겼다가 러너 디스크가 가득 차서 배포가 두 번 실패했다. 사이사이에 버전 옆 빌드 일시 표시와 AI 지시 창의 흐름 정리를 했다.

## 배경 — 전날 남긴 숙제

#55의 마지막에 정할 것을 세 가지 남겼다. 그중 둘이 러너 문제였다.

- develop에 푸시할 때마다 `local` 대상 CD가 자동으로 돌았다. 그런데 `baton-local` 러너가 등록돼 있지 않아 배포 단계에서 멈췄고, 하나뿐인 러너를 붙잡았다. 전날은 매번 손으로 취소했다.
- PR에서 따로 도는 CI는 여전히 GitHub 호스팅 러너를 썼다. 결제 문제로 호스팅 러너는 job을 시작하지 못한다. Dependabot PR의 체크가 전부 실패로 남아 있었다.

## 문제

1. develop 푸시는 무엇을 해야 하나. 버전만 올리나, 개발 서버에 배포까지 하나.
2. PR CI를 자체 러너로 옮기면 러너 한 대가 감당하나.
3. 화면에 떠 있는 것이 언제 빌드된 코드인지 어떻게 알 수 있나.
4. AI 지시 창이 복잡하다. 스크롤이 겹치고, 이전 단계로 돌아가는 길이 제각각이다.

## 결정 1 — develop 푸시는 개발 서버 배포다 (오전의 결정을 낮에 뒤집었다)

아침에는 가장 좁은 수정을 골랐다. develop 푸시일 때 `Delivery Plan` job을 건너뛰게 했다. 품질 검사, 이미지 게시, 배포가 모두 이 job 뒤에 달려 있어서 함께 건너뛴다. 푸시하고 지켜보니 패치 버전 올리기만 성공하고 나머지는 `skipped`로 끝났다.

한 시간 반 뒤에 질문이 들어왔다. "개발 서버 배포는 CI/CD에서 바로 되는 것 아니었나?" 아니었다. 원래 구성은 이랬다.

| 트리거 | 하던 일 |
| --- | --- |
| develop 푸시 | `local` 환경 배포 (러너가 없어 멈춤) |
| main 푸시 | 개발 서버 배포 |
| `vX.Y.Z` 태그 | 운영 배포 |

개발 서버 배포는 처음부터 develop 푸시와 연결돼 있지 않았다. 그동안은 수동 실행으로만 배포했다. 그런데 실제 작업은 전부 develop에서 일어나고, 확인하고 싶은 것도 develop의 최신 상태다.

그래서 오전의 조건을 빼고, develop 푸시의 배포 대상을 `local`에서 개발 서버로 바꿨다.

```yaml
# cd.yml — delivery-plan 단계
# The company development server follows develop; no baton-local runner exists.
environment="company-development"
```

동시 실행 그룹도 같은 환경을 쓰게 맞췄다. develop 배포와 main 배포가 같은 서버에 동시에 들어가지 않고 차례로 진행된다. 이 환경에는 승인 규칙이 없어서, 푸시하면 품질 검사부터 배포까지 사람 손 없이 끝난다.

첫 자동 배포는 28분 걸렸다. 러너가 하나라 pipeline, api, web 이미지를 하나씩 빌드한다.

> "멈추는 자동 실행"을 고치는 방법은 둘이다. 끄거나, 제대로 돌게 하거나. 오전에는 껐고, 쓰는 사람의 기대를 듣고 나서 제대로 돌게 했다.

## 결정 2 — PR CI도 자체 러너로

전날은 CD가 `ci.yml`을 부를 때만 자체 러너를 넘겼다. PR에서 직접 도는 CI는 `ubuntu-latest`였다. 이날 `ci.yml`의 job 9개가 모두 기본으로 자체 러너를 고르게 바꿨다. 다른 저장소가 불러 쓰는 `data-check.yml`은 그대로 뒀다.

Dependabot PR은 "다시 실행"으로는 살릴 수 없었다. 예전 실행을 다시 돌리면 그때의 워크플로 정의가 그대로 쓰여서 또 호스팅 러너로 간다. 그래서 develop 대상 PR 8개에 `@dependabot rebase` 댓글을 남겼다. 브랜치가 최신 develop 위로 올라와야 새 `ci.yml`이 적용된다.

결과는 이랬다. 웹 의존성 minor·patch 묶음(#29)이 자체 러너에서 처음으로 통과해서 머지했다. Actions 버전 올림 3건도 통과했다. vite 8, typescript 7 같은 메이저 올림은 실패했거나 rebase에 응답이 없었다. main 대상 PR 2건은 손대지 않았다. 러너 변경이 아직 develop에만 있기 때문이다.

이 결정에는 비용이 있다. 러너는 개발 서버 자체에서 돈다. CPU 2개, 메모리 7.7GB를 서비스 중인 BATON과 나눠 쓴다. PR 8개의 CI가 한 줄로 서면 그 뒤의 배포는 한 시간 넘게 기다린다.

## 결정 3 — 검사용 이미지는 실행마다 지운다

오후에 밀린 일을 점검하다가 개발 서버 배포가 두 번 연속 실패한 것을 알았다. #29 머지 배포와 AI 지시 창 변경 배포다. 둘 다 이미지 보안 검사 단계에서 같은 메시지로 멈췄다.

```text
no space left on device
```

호스팅 러너는 실행마다 새 머신이라 남는 것이 없다. 자체 러너는 다르다. Trivy로 검사하려고 로드한 `baton-scan-*` 이미지가 실행마다 그대로 남는다. PR CI까지 옮긴 날이라 실행 횟수가 크게 늘었고, 30GB 디스크가 반나절 만에 찼다.

서버에 직접 들어갈 수 없었기 때문에, 정리 단계를 CI에 넣고 그 실행으로 서버를 비웠다.

```yaml
# A self-hosted runner keeps every loaded scan image; left alone they fill its disk.
- name: Free runner disk from earlier scans
  if: runner.environment == 'self-hosted'
  shell: bash
  run: |
    set +e
    df -h / /tmp
    docker image ls --filter 'reference=baton-scan-*' --format '{{.Repository}}:{{.Tag}}' \
      | grep -v ":${GITHUB_SHA}$" | xargs -r docker image rm -f
    docker image prune -f
    docker builder prune -f
    docker system df
    exit 0
```

검사가 끝난 뒤에는 `if: always()`로 이번 실행의 검사용 이미지도 지운다. 성공이든 실패든 남기지 않는다.

| | 사용 | 여유 |
| --- | --- | --- |
| 정리 전 | 25GB (88%) | 3.6GB |
| 정리 후 | 21GB (75%) | 7.2GB |

검사용 이미지 16개가 지워졌고 배포는 통과했다. 아직 쓰이지 않는 이미지가 28개, 약 6.2GB 남아 있었다. 그래서 한 줄을 더 넣었다.

```yaml
# Images no container uses and that were built over a week ago; a rollback pulls them again.
docker image prune -a -f --filter 'until=168h'
```

기준은 "마지막 사용"이 아니라 이미지가 만들어진 시각이다. Docker가 지원하는 필터가 그것뿐이다. 일주일 넘은 버전으로 롤백하면 이미지를 레지스트리에서 다시 받게 된다. 그 정도는 받아들이기로 했다.

> 호스팅 러너에서 자체 러너로 옮기면 "실행이 끝나면 머신이 사라진다"는 전제가 함께 사라진다. 청소는 이제 워크플로의 일이다.

## 결정 4 — 버전 옆에 빌드 일시, 로컬에서는 커밋 시각

배포가 자동이 되니 "지금 떠 있는 것이 언제 것인가"가 궁금해진다. 버전 번호만으로는 부족했다. 버전 옆에 빌드 일시를 붙였다.

- CI가 이미지를 빌드할 때 `BATON_BUILD_TIME` 인자로 시각을 넣는다.
- 하단 상태 표시줄, 정보 창, 로그인 화면에 `v1.1.92 · 2026-11-24 10:23 빌드`처럼 나온다. 시각은 보는 사람의 브라우저 시간대로 바꿔 보여 준다.
- 로그인 전 첫 화면에서는 `/api/version`을 쓸 수 없다. 인증을 요구하기 때문이다. 그 화면이 원래 부르던 공개 설정 응답 `/api/auth/config`에 버전과 빌드 시각을 함께 넣었다.

로컬에서 띄우자 버전만 나오고 시각이 없었다. 빌드 인자가 없으니 당연한 결과인데, 보는 사람에게는 고장처럼 보인다. 후보는 둘이었다. API를 띄운 시각, 또는 마지막 커밋 시각. 띄운 시각은 코드가 언제 것인지 알려 주지 못한다. 커밋 시각을 골랐다.

| 실행 환경 | 표시 |
| --- | --- |
| CI가 만든 이미지 | `· 2026-11-24 10:23 빌드` |
| 로컬 실행 | `· 2026-11-24 10:13 커밋` |
| 둘 다 모를 때 | 버전만 |

꼬리말을 다르게 붙여서 두 시각이 헷갈리지 않게 했다. 커밋 시각은 API가 뜬 뒤 한 번만 읽는다. git이 없는 환경에서는 비워 둔다.

## 결정 5 — AI 지시 창은 스크롤 하나, 진입 하나, 돌아가는 길 하나

전날 패널 스크롤을 하나로 줄였는데도 "스크롤이 여러 개 생긴다"는 말이 다시 나왔다. 남은 곳은 안쪽이었다.

- 진행 로그 목록에 최대 높이 220px가 걸려 있어서 대화 스크롤 안에 세로 스크롤이 하나 더 생겼다. 높이 제한을 풀었다.
- JSON과 코드 블록은 줄을 접지 않아 블록마다 가로 스크롤이 생겼다. 긴 줄을 접게 했다.
- "정리할 목표" 입력칸은 두 줄 높이로 고정돼 있었다. 내용만큼 늘어나게 바꿨다.

입력칸에서 한 번 헛디뎠다. 처음에는 하단 입력칸이 패널 높이의 30%까지만 늘어나게 막았다. 긴 글을 넣으면 대화가 가려질까 봐서다. 그러자 30%를 넘는 글에서 입력칸 안에 스크롤이 다시 생겼다. 20분 뒤에 같은 지적을 또 받았다. 결국 높이 제한을 없애고, 하단 영역이 패널의 절반을 넘으면 하단 고정을 풀어 대화와 함께 흐르게 했다.

스크롤 다음은 흐름이었다.

- **이전 이력:** 지난 지시는 기본으로 접고 "이전 지시 N건 보기" 한 줄만 남긴다. 최근 요청과 검토 중인 변경안은 접어도 보인다.
- **단계 표시:** 번호 세 개로 줄이고, 그 아래에 지금 할 일을 한 문장으로 적는다.
- **요구사항 정리 진입:** 여러 곳에 흩어져 있던 진입을 "요구사항 먼저 정리" 버튼 하나로 줄였다.

저녁에는 "이전 단계로 돌아가는 흐름"을 코드로 따라가 봤다. 돌아갈 수는 있는데 단계마다 방법이 달랐다. 가장 아픈 것은 변경안을 취소하면 원래 지시가 사라지는 점이었다. 변경안이 만들어질 때 입력칸을 비우기 때문이다. 지시를 조금 고쳐 다시 요청하려면 처음부터 써야 했다.

네 가지를 고쳤다. 변경안을 취소하면 원래 지시를 입력칸에 다시 채운다. 단계 표시 줄에 돌아가기 버튼을 하나 둔다. 변경안 검토 중에 기록을 펼치면 왜 고칠 수 없는지 안내한다. 정리와 연결된 지시를 고치면 연결이 끊겼다고 알리고 되돌리는 버튼을 준다.

같은 질문이 프로젝트 단계(분석 → 설계 → 구현 → 시험 → 인도)로 이어졌다. 앞 단계의 산출물을 고치려면 그 단계로 복귀해야 하는데, 복귀하는 길이 보이지 않는다는 것이다. 조사해 보니 기능은 이미 있었다. 사유를 적으면 앞 단계로 돌아가고 그 단계 산출물의 잠금이 풀린다. 다만 버튼이 현황 탭의 표, 잠긴 문서의 배너, 실패한 게이트 창에만 있었다. 늘 보이는 탐색기 진행 카드에는 "다음 단계 →"만 있었다. 진입점을 평소 보이는 화면으로 끌어냈다.

> 기능이 있는 것과 길이 보이는 것은 다르다. 사용자가 "없다"고 말하면, 먼저 진입점이 어디 있는지 본다.

## 의도치 않은 함정 — 묵은 dev 서버가 포트를 쥐고 있었다

로그인 화면에 버전을 넣고 나서 로컬에서 확인이 되지 않았다. 원인은 코드가 아니었다. 전날 오전에 세션이 띄워 둔 Vite가 5173 포트를 계속 차지하고 있었다. 새로 띄운 것이 아니라 하루 묵은 프로세스가 응답하고 있었다.

세션이 띄운 API와 Web을 모두 내렸다. 그리고 앞으로 로컬 개발 서버는 직접 띄우기로 했다. 누가 띄웠는지 모르는 프로세스가 남으면, 화면이 안 바뀌는 이유를 코드에서 찾게 된다.

버전 문구를 바꾼 여파도 있었다. 프로젝트 선택 화면의 버전 문구를 기대하던 테스트 하나가 실패했다. 이번 변경 때문인지부터 확인한 뒤, 기대 문자열을 고쳐 별도 커밋으로 올렸다.

## 마무리

이날 develop에 올린 커밋은 버전 올림과 머지를 빼고 13개다. 오후에 디스크를 비우고 통과한 배포에서 개발 서버는 1.1.97이 됐다.

- develop에 푸시하면 품질 검사, 이미지 게시, 개발 서버 배포까지 자체 러너에서 자동으로 끝난다. PR CI도 같은 러너에서 돈다.
- 러너는 실행마다 검사용 이미지를 지우고, 일주일 넘은 미사용 이미지도 정리한다.
- 화면 어디서든 지금 떠 있는 코드의 버전과 시각을 볼 수 있다.

확인하지 못한 것도 적어 둔다. AI 지시 창과 단계 복귀 변경은 타입 검사, 빌드, 관련 테스트로만 확인했다. 화면에서 직접 눌러 본 것은 아니다. 입력칸이 내용만큼 늘어나는 동작은 Chrome과 Edge에서만 된다.

다음에 할 일은 세 가지다. 통과한 Actions 버전 올림 PR 3건을 머지하고, 실패한 메이저 올림 PR의 원인을 본다. main에도 러너 변경을 넣어 main 대상 PR의 CI를 살린다. 러너 한 대에 CI와 배포가 줄을 서는 구조가 계속 버틸지도 지켜봐야 한다.
